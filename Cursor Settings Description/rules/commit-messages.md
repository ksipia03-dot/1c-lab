# Правило `commit-messages` — формат сообщений коммитов

## Назначение правила

Правило регламентирует **формат сообщений коммитов** по спецификации [Conventional Commits](https://www.conventionalcommits.org/). Его цель — единообразная история git: по однородным сообщениям легко читать лог, автоматически генерировать changelog и понимать природу каждого изменения (фича, фикс, рефакторинг) без чтения самого diff.

Правило действует всякий раз, когда ассистент создаёт коммиты или предлагает сообщения для них.

## Разбор frontmatter

| Поле | Значение | Что означает |
|------|----------|--------------|
| `description` | `Conventional Commits format for consistent commit messages` | Краткое описание, по которому агент решает, нужно ли подключить правило. |
| `globs` | `[]` (пусто) | Масок файлов нет — правило **не** подключается автоматически по типу файла. |

**Как правило подключается к контексту агента.** Поскольку `globs` пустой, работает режим **Agent Requested**: правило не прикрепляется к контексту само по себе. Агент (или оркестратор) подключает его по описанию (`description`) в момент, когда задача касается коммитов — например, когда пользователь просит «закоммить изменения» или «сгенерируй сообщение коммита». Поле `alwaysApply` не задано, значит постоянного действия у правила нет.

Отличие от масочного режима: правила с заполненными `globs` (например, `security`, `testing`) подключаются автоматически, как только в контексте появляется файл подходящего типа (Auto Attached). Здесь же триггер — смысловой, а не файловый.

## Подробный пересказ содержимого оригинала

### Структура сообщения

```
<type>(<scope>): <subject>

[optional body]
```

Обязательный каркас: **тип**, опциональный **скоуп** в скобках, двоеточие и **тема**. Тело сообщения (body) — необязательно и отделяется пустой строкой.

### Типы коммитов (таблица из 8 типов)

| Тип | Назначение | Пример из оригинала |
|-----|-----------|---------------------|
| `feat` | Новая функциональность | `feat(auth): add OAuth login` |
| `fix` | Исправление бага | `fix(api): handle null response` |
| `docs` | Документация | `docs: update API readme` |
| `refactor` | Изменение кода без новой фичи и без фикса | `refactor: extract validation` |
| `test` | Добавление тестов | `test: add auth unit tests` |
| `chore` | Обслуживание (зависимости, конфиги) | `chore: update dependencies` |
| `perf` | Улучшение производительности | `perf: cache user queries` |
| `style` | Только форматирование | `style: fix indentation` |

Ключевой ориентир при выборе типа: `feat` — «add», `fix` — «handle/fix», `refactor` — код изменился, поведение — нет, `chore` — изменения вне кода продукта.

### Правила темы (Subject)

- Начинать **со строчной буквы**, **без точки** в конце.
- **Повелительное наклонение**: «add», а не «added» или «adds».
- Максимум **50 символов**.
- Контрольная проверка: тема должна грамматически достраивать фразу **«This commit will…»** («This commit will add quantity selector» — правильно).

### Скоуп (Scope, необязательный)

Указывает зону изменения:

- **Область функциональности**: `auth`, `api`, `ui`, `db`.
- **Компонент**: `button`, `header`, `user-service`.

### Примеры корректных сообщений

```bash
feat(cart): add quantity selector
fix(checkout): prevent double submission
refactor(db): extract query builders
docs(readme): update installation steps
```

Обратите внимание: скоуп может отсутствовать (тип `docs`/`refactor` без скобок в примерах типов выше) — это допустимо.

### Когда подключать скилл git-helper

Оригинал завершается перекрёстной ссылкой: использовать `.cursor/skills/git-helper/SKILL.md`, когда:

- пользователь просит сгенерировать сообщение коммита;
- пользователь просит закоммитить изменения;
- нужно проанализировать staged-изменения и составить подходящее сообщение;
- нужно определить правильный тип коммита по характеру изменений кода.

То есть правило задаёт **стандарт** (как должен выглядеть результат), а скилл `git-helper` — **процедуру** (как из diff получить такое сообщение).

## Связи с другими файлами

- **Скилл `git-helper`** (`.cursor/skills/git-helper/SKILL.md`) — главный потребитель этого правила: именно он реализует генерацию сообщений по Conventional Commits и вызывается при любых операциях коммита. Описание скилла: `Cursor Settings Description/skills/git-helper/`.
- **Правило `git-workflow`** — смежное: оно регламентирует ветки, атомарность коммитов и PR, а `commit-messages` — текст самих сообщений. Вместе покрывают весь git-процесс.
- **Агенты** `worker`, `debugger` и другие, чьи изменения завершаются коммитом, попадают под это правило в момент коммита.
- В **общей карте системы** (`README.md`, раздел 3.3) правило отнесено к группе «Agent Requested» вместе с `git-workflow`: оба подключаются по запросу агента, а не по маскам файлов.
