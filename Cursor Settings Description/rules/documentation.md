# Правило `documentation` — требования к документированию кода

## Назначение правила

Правило определяет, **когда и как документировать код**: какие конструкции обязаны иметь JSDoc-комментарий, какие документировать не нужно, и в каком формате писать. Цель — чтобы документация в коде была полезной и не превращалась в шум: описывается публичное и неочевидное, очевидное остаётся без комментариев.

Важно различать два уровня документации в системе: это правило касается **инлайн-документации в коде** (JSDoc), а проектную документацию в `ai_docs/` ведёт скилл `docs` и агент `documenter` — правило лишь указывает, когда к ним обращаться.

## Разбор frontmatter

| Поле | Значение | Что означает |
|------|----------|--------------|
| `description` | `Documentation requirements for code and functions` | Краткое описание содержимого правила. |
| `globs` | `["**/*.ts", "**/*.tsx", "**/*.js", "**/*.jsx"]` | Маски файлов, при работе с которыми правило подключается автоматически. |

**Как правило подключается к контексту агента.** Здесь работает режим **Auto Attached**: как только агент читает или правит файл TypeScript/JavaScript (`.ts`, `.tsx`, `.js`, `.jsx`), правило автоматически попадает в его контекст. Вручную вызывать его не нужно — Cursor сам прикрепляет правило по маске. Это правильный выбор: требования к JSDoc релевантны ровно тем файлам, где JSDoc существует.

Поле `alwaysApply` не задано — постоянно (для всех файлов и разговоров) правило не действует, только внутри масочных контекстов.

## Подробный пересказ содержимого оригинала

### Когда документировать (JSDoc)

**Всегда документировать:**

- **Публичные API** — то, чем пользуются другие модули/разработчики.
- **Сложные алгоритмы** — где по коду нельзя сходу понять логику.
- **Неочевидную бизнес-логику** — решения, продиктованные предметной областью.
- **Обходные пути и хаки** — обязательно с пометкой **TODO** на исправление (чтобы временный костыль не стал постоянным и не забылся).

**Не документировать:**

- **Самоочевидный код** — комментарий, повторяющий код словами, — мусор.
- **Приватные вспомогательные функции** — они не часть контракта.
- **Простые CRUD-операции** — create/read/update/delete без особой логики.
- **Геттеры/сеттеры** — тривиальный доступ к полям.

Принцип общий: документируется «почему» и контракт, а не «что делает эта строка».

### Формат (пример из оригинала)

```typescript
/**
 * Authenticates user with email and password.
 *
 * @param email - User's email address
 * @param password - Plain text password
 * @returns User object with session token
 * @throws {AuthError} If credentials are invalid
 */
async function login(email: string, password: string): Promise<AuthResult> {
  // ...
}
```

Стандарт JSDoc-блока:

- Первая строка — краткое описание функции (что делает, в повелительном/отглагольном стиле).
- `@param` — каждый параметр с пояснением.
- `@returns` — что возвращает.
- `@throws {ТипОшибки}` — какие исключения бросает и при каком условии (обязательно для функций с явными ошибками).

### Когда использовать скилл docs

Оригинал завершается перекрёстной ссылкой на `.cursor/skills/docs/SKILL.md`. Скилл нужен, когда:

- пользователь просит обновить или создать документацию;
- после реализации фичи (создание проектной документации);
- нужно понять структуру проектной документации (она сконфигурирована в `.cursor/config.json`, блок `documentation`);
- пользователь упоминает «documentation», «docs» или просит «задокументируй это».

Разграничение: **правило** говорит, как комментировать код инлайн; **скилл `docs`** объясняет, как устроена и как вести проектную документацию в `ai_docs/`.

## Связи с другими файлами

- **Скилл `docs`** (`.cursor/skills/docs/SKILL.md`) — напарник правила: правило регулирует JSDoc в коде, скилл — структуру `ai_docs/` (планы, отчёты, архитектура). Описание скилла: `Cursor Settings Description/skills/docs/`.
- **`config.json`** — пути документации (`ai_docs/develop/...`) и переключатели типов документации заданы в блоке `documentation`; правило ссылается на эту конфигурацию косвенно через скилл.
- **Агент `documenter`** — ведёт проектную документацию в `ai_docs/` после завершения работ; правило задаёт ему нижнюю планку качества для инлайн-комментариев в коде, который он описывает.
- **Агент `worker`** — в его инструкции продублированы те же нормы: JSDoc только для публичных функций, никакой markdown-документации от него. Правило и инструкция агента усиливают друг друга: правило срабатывает автоматически на файлах `.ts/.tsx/.js/.jsx`, инструкция — встроена в самого агента.
- **Агент `reviewer`** — при ревью проверяет соблюдение стандартов, включая комментарии «почему, а не что» (см. чек-лист в скилле `code-quality-standards`).
