# Правило `security` — критичные правила безопасности

## Назначение правила

Правило фиксирует **минимальный недоговороспособный набор правил безопасности**, предотвращающих катастрофы: утечку секретов, инъекции, компрометацию паролей. Это самое короткое из пяти правил — и самое жёсткое по тону: вместо рекомендаций здесь два списка **NEVER** (никогда) и **ALWAYS** (всегда).

Правило не исчерпывает тему безопасности — оно задаёт «красные линии», а глубокие практики вынесены в скилл `security-guidelines`, на который правило ссылается.

## Разбор frontmatter

| Поле | Значение | Что означает |
|------|----------|--------------|
| `description` | `Critical security rules that prevent disasters` | Краткое описание: правила, предотвращающие катастрофы. |
| `globs` | `["**/*.ts", "**/*.tsx", "**/*.js", "**/*.jsx", "**/*.py", "**/*.go"]` | Маски файлов, на которых правило подключается автоматически. |

**Как правило подключается к контексту агента.** Режим **Auto Attached**: как только агент работает с файлом TypeScript, JavaScript, Python или Go, правило автоматически оказывается в его контексте — ничего вызывать вручную не нужно. Список масок самый широкий среди всех правил (6 масок, включая `.py` и `.go`), потому что риски безопасности существуют в любом исполняемом коде, а не только во фронтенд-стеке.

Поле `alwaysApply` не задано — вне перечисленных типов файлов правило не активно (например, при правке markdown-документации оно в контекст не попадёт).

## Подробный пересказ содержимого оригинала

### NEVER — пять абсолютных запретов

- ❌ **Коммитить секреты/API-ключи/токены в git.** Попавший в историю git секрет считается скомпрометированным навсегда — удаление файла новым коммитом историю не очищает.
- ❌ **Использовать `eval()` или `Function()` на пользовательском вводе.** Прямой путь к выполнению произвольного кода (code injection).
- ❌ **Хранить пароли открытым текстом.** Только хеширование — **bcrypt** или **argon2**.
- ❌ **Конкатенировать SQL-строки.** Только **параметризованные запросы** — иначе SQL-инъекция.
- ❌ **Доверять только клиентской валидации.** Клиент контролируется пользователем; любую проверку на клиенте можно обойти.

### ALWAYS — три обязательных требования

- ✅ **Валидировать весь пользовательский ввод на сервере.** Сервер — единственная доверенная сторона; клиентская валидация — лишь UX-удобство поверх.
- ✅ **Использовать HTTPS в продакшене.** Трафик между клиентом и сервером обязан быть зашифрован.
- ✅ **Добавлять `.env` в `.gitignore`.** Профилактика первого запрета из NEVER: файлы окружения с секретами не должны иметь шанса попасть в индекс git.

Логика списков: NEVER — действия, которые создают уязвимость мгновенно; ALWAYS — привычки, без которых уязвимость возникает рано или поздно.

### Когда ОБЯЗАТЕЛЬНО читать скилл security-guidelines

Оригинал использует усиление **«MUST read»** — обязательно прочитать `.cursor/skills/security-guidelines/SKILL.md` при:

- реализации **аутентификации/авторизации**;
- создании **API-эндпоинтов**;
- обработке **пользовательского ввода или загрузки файлов**;
- работе с **чувствительными данными** (пароли, PII, платёжная информация, токены);
- использовании **внешних API**;
- реализации **сессий или cookies**.

То есть правило — это трипвайр: оно срабатывает на любом коде, а в перечисленных рискованных зонах требует углубиться в полный гайдлайн.

## Связи с другими файлами

- **Скилл `security-guidelines`** (`.cursor/skills/security-guidelines/SKILL.md`) — главный напарник: правило даёт критичные запреты, скилл — полные практики (auth, API, данные). Связь прямая: правило предписывает читать скилл (MUST read). Описание скилла: `Cursor Settings Description/skills/security-guidelines/`.
- **Агент `security-auditor`** — специалист, проверяющий auth, платежи, API-эндпоинты, загрузку файлов, работу с паролями/токенами/PII: его зона ответственности дословно совпадает со списком MUST read этого правила.
- **Агент `worker`** — в его инструкции продублировано требование читать `security-guidelines` при работе с auth/API/чувствительными данными. Правило страхует: даже если worker забудет, оно автоматически подключится на файлах `.ts/.tsx/.js/.jsx/.py/.go`.
- **Правило `git-workflow`** — пересечение в запрете коммитить секреты: там это пункт списка Don't, здесь — первый пункт NEVER. Двойная фиксация самого опасного нарушения.
- **Скилл `audit-workflow`** (команда `/audit`) — включает аудит безопасности через `security-auditor`; это правило — тот минимум, по которому аудит проверяет в первую очередь.
- В **общей карте системы** (`README.md`, раздел 3.3) правило описано как «критичные правила безопасности, предотвращающие катастрофы» из группы Auto Attached.
