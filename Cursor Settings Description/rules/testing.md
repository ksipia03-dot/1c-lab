# Правило `testing` — стандарты тестирования

## Назначение правила

Правило задаёт **стандарты написания и структуры тестов**: пропорции видов тестов (пирамида), внутреннее устройство теста (AAA), что тестировать, а что — нет, и политику моков. Цель — тестовый набор, который быстро работает, ловит реальные баги и не рассыпается от рефакторинга.

## Разбор frontmatter

| Поле | Значение | Что означает |
|------|----------|--------------|
| `description` | `Testing standards and test structure guidelines` | Краткое описание содержимого правила. |
| `globs` | `["**/*.test.ts", "**/*.test.tsx", "**/*.spec.ts", "**/*.spec.tsx", "**/tests/**", "**/__tests__/**"]` | Маски тестовых файлов и папок. |

**Как правило подключается к контексту агента.** Режим **Auto Attached**, но с узкой специализацией: правило прикрепляется автоматически, только когда агент работает с **тестовыми** файлами — по суффиксам `.test.ts`, `.test.tsx`, `.spec.ts`, `.spec.tsx` или внутри папок `tests/` и `__tests__/`. При правке обычного продуктового кода оно в контекст не попадает — там требования к тестам приходят другим путём (через инструкции агента `test-writer` и ворота test-runner).

Это самый длинный список globs среди правил (6 масок), что отражает разнообразие соглашений о расположении тестов в разных фреймворках. Поле `alwaysApply` не задано — постоянного действия нет.

## Подробный пересказ содержимого оригинала

### Пирамида тестов

```
         /\
        /  \     E2E (few)
       /────\
      /      \   Integration (some)
     /────────\
    /          \ Unit (many)
   /────────────\
```

Классическая пропорция «много дешёвых — мало дорогих»:

- **Unit-тесты** — быстрые, изолированные, их **много**. Основа набора.
- **Интеграционные тесты** — проверяют модули **в связке**, их **некоторое количество**.
- **E2E-тесты** — только **критичные пользовательские пути**, их **мало** (медленные и хрупкие).

Смысл: чем выше уровень, тем дороже запуск и поддержка — поэтому основная масса проверок должна жить на уровне unit.

### Структура теста — AAA

Каждый тест строится по трём блокам **Arrange → Act → Assert** (пример из оригинала):

```typescript
it('should calculate total with discount', () => {
  // Arrange - Setup data
  const cart = new Cart();
  cart.addItem({ price: 100, quantity: 2 });

  // Act - Execute code
  const total = cart.calculateTotal(0.1);

  // Assert - Verify result
  expect(total).toBe(180);
});
```

- **Arrange** — подготовить данные и окружение.
- **Act** — выполнить ровно одно тестируемое действие.
- **Assert** — проверить результат.

Имя теста формулируется как «should …» — «should calculate total with discount».

### Что тестировать

**Всегда тестировать:**

- Публичные API и функции.
- Бизнес-логику.
- Граничные случаи и обработку ошибок.
- Трансформации данных.

**Не тестировать:**

- Приватные методы — их проверяют **через публичный API** (иначе тесты ломаются при каждом рефакторинге внутренностей).
- Код фреймворков и библиотек — он уже протестирован авторами.
- Сторонние интеграции — их **мокают**.
- Простые геттеры/сеттеры — тестировать там нечего.

Общий принцип: тестируется **наблюдаемое поведение и контракт**, а не реализация.

### Мокинг (Mocking)

**Когда мокать:**

- Внешние сервисы (API, базы данных).
- Код, зависящий от времени.
- Случайные значения.
- Операции файловой системы.

**Когда НЕ мокать:**

- Сам тестируемый код (мокать его — значит не тестировать ничего).
- Простые чистые функции.
- Структуры данных.

Критерий простой: мокают **недетерминированное и внешнее**, не мокают **детерминированное и своё**.

## Связи с другими файлами

- **Агент `test-writer`** — главный исполнитель этого правила: пишет тесты на код worker'а, следуя пирамиде, AAA и политике моков. Правило — его стандарт качества.
- **Агент `test-runner`** — гоняет линтер и тесты, проверяет критерии приёмки; требование правила «тесты проходят» — его ворота. При провале код уходит агенту `debugger` (до 3 попыток по воркфлоу `orchestration`).
- **Правило `git-workflow`** — дублирует требование с другой стороны: «Tests pass at every commit» и чек-лист «Run tests» перед коммитом. Коммит с красными тестами нарушает оба правила.
- **Скилл `code-quality-standards`** — его чек-лист ревью содержит пункт «Tests cover main scenarios», а чек-лист рефакторинга требует наличия тестов **до** начала правок — страховка неизменности поведения.
- **Скиллы `orchestration` и `simple-workflow`** (команды `/orchestrate`, `/implement`) — в их конвейерах этап «Тест» обязателен: test-writer пишет тесты, test-runner проверяет. Правило определяет, каким должен быть результат этого этапа.
- В **общей карте системы** (`README.md`, раздел 3.3) правило описано как «стандарты тестирования и структура тестов» из группы Auto Attached.
