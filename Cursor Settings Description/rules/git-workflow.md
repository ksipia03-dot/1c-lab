# Правило `git-workflow` — стандарты git-процессов

## Назначение правила

Правило регламентирует **весь git-процесс**: именование веток, стратегию ветвления, практики коммитов, правила pull request'ов и списки «можно/нельзя». Цель — предсказуемая и безопасная совместная работа: понятные ветки, атомарные коммиты, обозримые PR и отсутствие разрушительных операций вроде force push в `main`.

## Разбор frontmatter

| Поле | Значение | Что означает |
|------|----------|--------------|
| `description` | `Git workflow standards for branch naming, commits, and PRs` | Краткое описание, по которому агент находит правило. |
| `globs` | `[]` (пусто) | Масок файлов нет — автоматического прикрепления по типу файла не происходит. |

**Как правило подключается к контексту агента.** Пустой `globs` означает режим **Agent Requested**: правило подключается не по файлам, а по смыслу задачи — когда пользователь или оркестратор работают с git (создание ветки, коммит, PR, разрешение конфликта). Агент решает подключить правило, сверив задачу с полем `description`. Постоянного действия (`alwaysApply`) у правила нет.

Сравнение: правила `testing`, `security`, `documentation` срабатывают автоматически на файлах по маскам (Auto Attached), а `git-workflow` и `commit-messages` — только по запросу, потому что git-операции не привязаны к типу редактируемого файла.

## Подробный пересказ содержимого оригинала

### Именование веток

Формат: `<type>/<short-description>`.

| Тип | Назначение | Пример из оригинала |
|-----|-----------|---------------------|
| `feature/` | Новая функциональность | `feature/user-auth` |
| `fix/` | Исправление багов | `fix/login-redirect` |
| `hotfix/` | Срочный фикс в продакшене | `hotfix/payment-crash` |
| `refactor/` | Улучшение кода | `refactor/api-layer` |
| `docs/` | Документация | `docs/api-readme` |
| `test/` | Добавление тестов | `test/auth-coverage` |
| `chore/` | Обслуживание | `chore/update-deps` |

Правила имени: только **строчные буквы**; **дефисы** вместо пробелов; коротко, но осмысленно; при наличии тикета — **включить его номер**: `feature/AUTH-123-oauth`.

### Стратегия ветвления

- `main` — продакшен-готовый код.
- `develop` — интеграционная ветка (**опционально**).
- Фича-ветки вливаются в `main` **через PR** — прямых коммитов в `main` процесс не предполагает.

### Практики коммитов

**Атомарные коммиты** — три требования:

- Один логический изменение на коммит.
- Проект **компилируется** на каждом коммите.
- **Тесты проходят** на каждом коммите.

**Перед коммитом** (3 шага): 1) прогнать тесты; 2) прогнать линтер; 3) просмотреть изменения `git diff`.

### Правила Pull Request

**Чек-лист перед созданием PR:**

- [ ] Тесты проходят.
- [ ] Код самопроверен автором.
- [ ] Ветка актуализирована относительно `main`.
- [ ] Нет конфликтов слияния.

**Размер PR:**

- **Идеально**: меньше 400 строк.
- **Максимум**: 1000 строк.
- Большие изменения — разбивать на несколько PR.

### Don't — запреты (6 штук)

- ❌ Force push в `main`.
- ❌ Коммитить секреты и креды.
- ❌ Коммитить большие бинарные файлы.
- ❌ Создавать огромные PR.
- ❌ Оставлять WIP-коммиты в PR.
- ❌ Мержить без ревью.

### Do — обязательные практики (4 штуки)

- ✅ Писать осмысленные сообщения коммитов (детализация — в правиле `commit-messages`).
- ✅ Держать PR сфокусированными.
- ✅ Обновлять ветку перед мержем.
- ✅ Удалять ветку после мержа.

### Когда использовать скилл git-helper

Перекрёстная ссылка на `.cursor/skills/git-helper/SKILL.md`. Скилл нужен при: генерации сообщений коммитов из staged-изменений; разрешении merge-конфликтов; потребности в конкретных git-командах (`cherry-pick`, `stash`, `bisect`, `rebase`); создании и управлении ветками; отмене операций (`reset`, `revert`, `restore`); исследовании истории (`blame`, `log`, `bisect`).

## Связи с другими файлами

- **Скилл `git-helper`** — процедурный напарник: правило задаёт стандарты (как называть ветки, какие PR допустимы), скилл даёт команды и приёмы для их выполнения. Описание: `Cursor Settings Description/skills/git-helper/`.
- **Правило `commit-messages`** — смежное: регламентирует текст сообщений коммитов, на который `git-workflow` ссылается пунктом «Write meaningful commit messages». Оба правила — режим Agent Requested.
- **Правило `security`** — пересечение в запретах: «не коммитить секреты» дублируется там же (NEVER-секция), что создаёт двойную защиту от утечки кредов.
- **Агенты `worker`, `debugger`, `refactor`** — их правки завершаются коммитами и ветками, поэтому при git-операциях они обязаны следовать этому правилу.
- В **общей карте системы** (`README.md`, раздел 3.3) правило описано как регламент «именование веток, атомарные коммиты, размеры PR, запреты (force push в main, секреты в коммитах)».
