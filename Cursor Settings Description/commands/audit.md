# Команда `/audit` — аудит здоровья проекта

## Назначение и как вызвать

`/audit` — команда **проверки здоровья проекта**: запускает три независимых анализа — **Архитектура → Безопасность → Качество кода** — и собирает их в **единый консолидированный отчёт** с оценкой здоровья (Health Score 0–10). Если найдены критические проблемы, предлагает запустить исправления в том же чате (фаза Remediation — только с подтверждения пользователя).

Как вызвать в чате:

- `/audit` — весь проект (по умолчанию `src/` или корень);
- `/audit src/services/` — конкретная директория;
- `/audit src/auth.ts` — один файл (очень тщательная проверка);
- `/audit --since main` — только файлы, изменённые относительно ветки main;
- `/audit --since HEAD~10` — изменения последних 10 коммитов.

Для вариантов `--since` скилл велит выполнить `git diff --name-only [ref]`, получить список файлов и передать его всем агентам как скоуп. Если скоуп не указан — по умолчанию основная папка исходников (проверить `package.json`, `src/`, `app/`, при неоднозначности — спросить пользователя).

Для каких задач предназначена: проверка здоровья проекта **перед релизом**, **онбординг** на незнакомую кодовую базу, **периодический контроль качества**, проверка **до/после крупного архитектурного изменения**.

## Когда использовать и когда НЕ использовать

- Нужна полная проверка проекта по трём осям (архитектура/безопасность/качество) → `/audit`.
- Нужно проверить конкретные изменения перед коммитом/PR → `/review` (легче и быстрее).
- Нужно структурно улучшить конкретный файл/модуль → `/refactor`.
- Нужно что-то реализовать → `/implement` или `/orchestrate` — `/audit` ничего не создаёт, он только анализирует (фазы 1–4 строго read-only).

## Главный запрет оригинала

Оригинал открывается блоком **«⛔ YOU ARE FORBIDDEN FROM DOING ANY WORK YOURSELF»**:

- **НЕ анализировать код. НЕ писать отчёты. НЕ редактировать файлы. НЕ запускать инструменты напрямую.**
- Каждый шаг выполняется субагентом через инструмент `Task`.
- Ассистент — только координатор: «Если ты собрался сделать что-либо, кроме вызова `Task`, — СТОП».

Дальше — блок **«MANDATORY: Read and follow the skill»**: прочитать `.cursor/skills/audit-workflow/SKILL.md` инструментом Read **прямо сейчас, до всего остального**; исполнить скилл в точности, вызывая `Task(subagent_type=...)` на каждом шаге; **не пропускать, не сокращать и не «пересказывать» шаги скилла**.

## Запускаемый скилл и цепочка агентов

Команда — тонкая обёртка над скиллом **`audit-workflow`** (`.cursor/skills/audit-workflow/SKILL.md`). Цепочка:

`/audit` → скилл `audit-workflow` → определение скоупа → **senior-reviewer** (архитектура) → **security-auditor** (безопасность) → **reviewer** (качество кода) → агрегация серьёзности → **documenter** (сводный отчёт) → при критических проблемах и подтверждении пользователя — фаза Remediation (**refactor** для структурных проблем, **planner + worker** для безопасности, **test-runner** для проверки, **documenter** для обновления отчёта).

**Важно:** фазы 1–4 всегда read-only; фаза 5 (исправления) запускается только с явного подтверждения пользователя. Фазы анализа последовательны — каждый агент получает контекст предыдущего, чтобы не дублировать находки.

### Пересказ скилла `audit-workflow`

**Шаг 1 — Define Scope.** Разбор ввода пользователя (варианты вызова выше); определение скоупа по умолчанию.

**Шаг 2 — Architecture Review (senior-reviewer).** Цель: структурные и дизайн-проблемы. Чек-лист: соблюдение SOLID; слоистая архитектура (разделение ответственности, направление зависимостей); использование паттернов (корректное/отсутствующее/неуместное); границы модулей и связанность; циклические зависимости; God-классы/модули; масштабируемость (стейтфул-компоненты, кэширование, узкие места); овер-инжиниринг и преждевременные абстракции. Вывод — список находок с ID `[A1]`, `[A2]`… по градациям Critical/High/Medium/Low.

**Шаг 3 — Security Audit (security-auditor).** Цель: уязвимости и риски. Контекст: сводка архитектурных находок (фокус на рискованных зонах — auth, API-слой). Чек-лист: потоки аутентификации/авторизации; валидация и санитизация ввода (инъекции, XSS); захардкоженные секреты/токены/креды; покрытие OWASP Top 10; безопасность эндпоинтов (rate limiting, CORS, ограничения методов); работа с чувствительными данными (PII, пароли, токены); уязвимости зависимостей (`npm audit` и т.п.); утечка внутренних деталей в сообщениях об ошибках. Вывод — находки `[S1]`, `[S2]`… по градациям.

**Шаг 4 — Code Quality Review (reviewer).** Цель: качество кода, поддерживаемость, техдолг. Контекст: сводки архитектуры и безопасности (чтобы не флагать уже найденное). Чек-лист: нарушения DRY (дубли, copy-paste); сложность (функции >30 строк, вложенность >3 уровней); ясность имён; дыры в обработке ошибок (проглоченные ошибки, пропущенные null-проверки); мёртвый код и неиспользуемые импорты; пробелы в тестовом покрытии критических путей; TypeScript (`any`, отсутствующие/неверные типы); комментарии (отсутствуют/вводят в заблуждение/устарели). Вывод — находки `[Q1]`, `[Q2]`…

**Шаг 5 — Severity Aggregation.** Слияние всех находок и подсчёт по градациям. **Формула Health Score (0–10):** старт с 10; −2 за каждую Critical (макс −6); −0.5 за каждую High (макс −3); −0.1 за каждую Medium (макс −1); пол на 0, округление до 1 знака.

**Шаг 6 — Consolidated Report (documenter).** Путь отчёта определяется через `.cursor/config.json`: если `documentation.enabled.audits` включён и задан `documentation.paths.audits` — сохранить как `ai_docs/develop/audits/YYYY-MM-DD-{scope-slug}-audit.md`; иначе — fallback в `{workspace.path}/audits/`. Формат отчёта: заголовок с датой/скоупом/аудиторами; Executive Summary с Health Score и сводной таблицей по градациям; секции Critical/High/Medium/Low с локациями и предлагаемыми фиксами; **Priority Matrix** (ID — проблема — серьёзность — трудоёмкость — приоритет P0/P1…); Next Steps (немедленно / этот спринт / следующий спринт / бэклог) с подсказками «используй `/refactor [file]` для структурных проблем, `/implement [fix]` для фиксов безопасности уровня фичи».

**Audit Scope Guide:** один файл — очень тщательно, быстро; модуль (5–10 файлов) — тщательно; большая директория (20–50 файлов) — сбалансированно; весь проект — высокоуровнево + глубоко в критических зонах. Для больших кодовых баз агенты фокусируются на самых критичных 20–30% файлов (бизнес-логика, auth, API), а не на конфигах, сгенерированном коде и тестах.

**Фаза 5 — Remediation Routing (только при критических находках + подтверждение пользователя).** После отчёта показать сводку критических проблем и спросить «Start remediation? (y/n)» — **ждать ответа, ничего не делая**. Категоризация: **Bucket A — структура/качество** (циклические зависимости, God-классы, глубокая вложенность/длинные функции, дубли, нарушения SOLID, запахи кода) → агент `refactor` с правилом «без смены поведения, все тесты должны проходить», затем проверка `test-runner`'ом (при падении — `debugger`, до 3 попыток). **Bucket B — безопасность/поведение** (захардкоженные секреты, отсутствующая валидация, дыры в auth/authz, отсутствующий rate limiting, любые фиксы, требующие новой логики) → `planner` строит план исправлений (одна проблема = одна задача), затем для каждой задачи стандартный цикл: `worker` → `test-writer` → `test-runner` (при падении — `debugger`, до 3 попыток) → `security-auditor` верифицирует конкретный фикс (при проблемах — `debugger`, до 3 попыток). После всех фиксов `documenter` добавляет в отчёт секцию «## Remediation Applied» (исправлено / осталось).

**Что аудит НЕ исправляет автоматически:** проблемы High/Medium/Low (только отчёт); проблемы, требующие крупного редизайна архитектуры (сначала обсуждение с пользователем); проблемы в стороннем/vendor-коде. Для оставшегося: `/refactor [file]` на конкретные структурные проблемы или `/orchestrate` для большого плана исправлений.

## Связи с другими файлами

- **Читает**: скилл `audit-workflow` (`.cursor/skills/audit-workflow/SKILL.md`); `git diff` для вариантов `--since`.
- **Вызывает агентов**: анализ — `senior-reviewer`, `security-auditor`, `reviewer`; отчёт — `documenter`; исправления — `refactor`, `planner`, `worker`, `test-writer`, `test-runner`, `debugger`, повторный `security-auditor`.
- **Читает конфиг**: `.cursor/config.json` (пути `documentation.paths.audits`, `enabled.audits`, `workspace.path`).
- **Пишет отчёты**: `ai_docs/develop/audits/` (или fallback в workspace).
- **Маршрутизирует на другие команды**: рекомендует `/refactor`, `/implement`, `/orchestrate` для оставшихся проблем (см. `refactor.md`, `implement.md`, `orchestrate.md`).
