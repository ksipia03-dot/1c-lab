# Команда `/review` — отдельное ревью кода

## Назначение и как вызвать

`/review` — команда **точечного ревью кода**: запускает воркфлоу **Ревью → (опционально авто-фикс) → Проверка**. Самая «лёгкая» из команд качества — в отличие от `/audit`, это не полный аудит проекта, а прицельная проверка конкретных изменений или файлов.

Как вызвать в чате (варианты скоупа из скилла):

- `/review` — staged-изменения (pre-commit ревью);
- `/review src/components/` — конкретная директория;
- `/review src/auth.ts` — один файл;
- `/review --staged` — явно только staged-изменения;
- `/review --last-commit` — изменения последнего коммита.

Разрешение скоупа по умолчанию: если скоуп не указан — **staged-изменения** (`git diff --staged`); если ничего не staged — **недавние изменения** (`git diff HEAD`); если и их нет — спросить у пользователя, какие файлы проверить.

Для каких задач предназначена: **перед коммитом** (pre-commit ревью); **после завершения фичи, перед созданием PR**; когда reviewer внутри `/orchestrate` что-то пометил, а нужен отдельный фикс; **быстрая sanity-проверка** конкретного файла.

## Когда использовать и когда НЕ использовать

Из секции «When to Use» скилла `review-workflow`:

**Подходит:** pre-commit ревью (`git diff --staged` перед коммитом); один файл после быстрой правки; ветка PR против main.

**НЕ подходит:**

- Полная проверка здоровья проекта → `/audit`;
- Плановые архитектурные улучшения → `/refactor`;
- Реализация новых фич → `/implement` или `/orchestrate`;
- Вся кодовая база или оценка архитектуры целого модуля → `/audit`.

## Главный запрет оригинала

Оригинал открывается блоком **«⛔ YOU ARE FORBIDDEN FROM DOING ANY WORK YOURSELF»**:

- **НЕ ревьюить код самому. НЕ редактировать файлы. НЕ запускать тесты напрямую.**
- Каждый шаг выполняется субагентом через инструмент `Task`.
- Ассистент — только координатор: «Если ты собрался сделать что-либо, кроме вызова `Task`, — СТОП».

Дальше — блок **«MANDATORY: Read and follow the skill»**: прочитать `.cursor/skills/review-workflow/SKILL.md` инструментом Read **прямо сейчас, до всего остального**; исполнить скилл в точности, вызывая `Task(subagent_type=...)` на каждом шаге; **не пропускать, не сокращать и не «пересказывать» шаги скилла**.

## Запускаемый скилл и цепочка агентов

Команда — тонкая обёртка над скиллом **`review-workflow`** (`.cursor/skills/review-workflow/SKILL.md`). Цепочка:

`/review` → скилл `review-workflow` → разрешение скоупа → **reviewer** → при критических проблемах (или согласии пользователя на фикс качества) → **debugger** → **test-runner** (проверка, при падениях снова **debugger**, до 3 попыток).

### Пересказ скилла `review-workflow`

**Шаг 0 — Resolve Scope.** Разобрать аргументы команды (варианты выше) с цепочкой умолчаний: staged → recent → спросить пользователя.

**Шаг 1 — Code Review (ОБЯЗАТЕЛЬНО: `Task` с `subagent_type="reviewer"`).** В промпте указать скоуп; попросить проверить: баги, проблемы безопасности, нарушения DRY и SOLID, сложность, именование, обработку ошибок, проблемы TypeScript; категоризировать находки как **Critical / Quality / Suggestion**; требовать конкретные пути файлов и номера строк. Дальнейшие ветки:

- **Нет проблем** → отчёт «✅ clean» пользователю и стоп.
- **Только Suggestions/Quality (некритичные)** → показать находки и спросить: «Fix these now?» (тогда шаг 2) или «Just report» (стоп, больше ничего не делать).
- **Найдены Critical** → всегда переходить к шагу 2 (при большом скоупе — сначала спросить пользователя).

**Шаг 2 — Auto-Fix (условный; ОБЯЗАТЕЛЬНО: `Task` с `subagent_type="debugger"`).** Запускается только если: найдены критические проблемы ИЛИ пользователь согласился чинить quality-проблемы. В промпте — списки критических и (при одобрении) качественных проблем, список файлов; ограничения для debugger'а: «чинить каждую проблему, НЕ рефакторить сверх необходимого для фикса, НЕ добавлять новые фичи». Дождаться завершения, извлечь, что было исправлено.

**Шаг 3 — Verification (условный; ОБЯЗАТЕЛЬНО: `Task` с `subagent_type="test-runner"`).** Запускается, только если шаг 2 выполнялся (были применены фиксы). В промпте — изменённые файлы и сводка фиксов; запустить линтер + тесты. При падении тестов — снова `Task(subagent_type="debugger")` с деталями ошибок → повторный test-runner; **максимум 3 попытки**; если всё ещё падает — отчёт пользователю.

**Important Rules скилла:**

1. **НЕ писать код самому** — ты координатор, не исполнитель.
2. **НЕ редактировать файлы самому** — все изменения только через субагентов.
3. **КАЖДЫЙ шаг ОБЯЗАН использовать `Task`** с корректным `subagent_type`.
4. **Всегда спрашивать перед фиксом** некритичных (quality/suggestion) проблем.
5. **Передавать контекст дальше** — сообщать каждому агенту, что нашёл/сделал предыдущий.

**Progress Reporting.** После каждого вызова субагента докладывать пользователю: что ревьюилось (файлы/скоуп); разбор находок (critical / quality / suggestions); применялись ли фиксы; финальный статус: ✅ чисто / ⚠️ остались проблемы / ❌ падения. Пример из скилла: ревью staged-изменений (3 файла) → reviewer нашёл 1 critical (null pointer в `user.ts:45`), 2 quality, 1 suggestion → debugger исправил critical + quality → test-runner: всё зелёное → итог «3 проблемы исправлены, 1 suggestion оставлена на потом».

## Связи с другими файлами

- **Читает**: скилл `review-workflow` (`.cursor/skills/review-workflow/SKILL.md`); `git diff --staged` / `git diff HEAD` для скоупа по умолчанию.
- **Вызывает агентов**: `reviewer` → (условно) `debugger` → (условно) `test-runner`.
- **Альтернативы-соседи**: `audit.md` (полная проверка проекта), `refactor.md` (структурные улучшения), `implement.md` и `orchestrate.md` (реализация нового).
- **Связь с оркестрацией**: внутри `/orchestrate` ревью каждой задачи тоже делает `reviewer`; `/review` нужен, когда ту же проверку хочется выполнить отдельно, вне полного цикла.
