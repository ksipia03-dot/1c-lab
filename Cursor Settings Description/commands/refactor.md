# Команда `/refactor` — безопасный рефакторинг с проверкой тестами

## Назначение и как вызвать

`/refactor` — команда **структурного улучшения кода без изменения поведения**: запускает воркфлоу **Анализ → Рефакторинг → Проверка → Документация**. Анализ целей делает senior-reviewer, сами правки — агент refactor, неизменность поведения подтверждает test-runner.

Как вызвать в чате (варианты скоупа из скилла):

- `/refactor src/utils/helpers.ts` — один файл;
- `/refactor src/services/` — директория;
- `/refactor "Extract auth logic from UserService"` — по намерению (intent-based);
- `/refactor` (без аргументов) — по недавним изменениям из git (`git diff`).

Если скоуп неясен — скилл велит спросить у пользователя файлы, директорию или цель.

Для каких задач предназначена: когда **качество кода мешает развитию фичи**; когда **ревью или senior-reviewer нашли структурные проблемы**; **после добавления тестового покрытия** к ранее непокрытому модулю; как продолжение `/audit` по конкретным структурным находкам.

## Когда использовать и когда НЕ использовать

Таблица «Refactor vs Rewrite Decision» из скилла:

| Сигнал | Рекомендация |
|--------|--------------|
| Код сложный, но тесты проходят | Рефакторить (безопасно) |
| У кода нет тестов | Сначала добавить тесты через `/implement` |
| Логика неверна И запутана | Сначала починить баги (`/implement`), потом рефакторить |
| Модулю нужен совершенно другой дизайн | Обсудить с пользователем — возможно, нужен `/orchestrate` |
| Меняется публичный API | Это НЕ рефакторинг — использовать `/orchestrate` |

**Scope Sizing** (держать сессию сфокусированной): одна функция или один файл — идеально; один модуль/директория (3–5 файлов) — нормально; несколько модулей (6–10 файлов) — разбить на сессии; вся кодовая база (>10 файлов) — слишком много, сузить скоуп. Крупные рефакторинги разбиваются на несколько сессий `/refactor`, каждая — по одному модулю или проблеме.

Противопоставление другим командам: для реализации нового — `/implement` или `/orchestrate`; для разовой проверки изменений — `/review`; для общего аудита проекта — `/audit`.

## Главный запрет оригинала

Оригинал открывается блоком **«⛔ YOU ARE FORBIDDEN FROM DOING ANY WORK YOURSELF»**:

- **НЕ анализировать код. НЕ рефакторить файлы. НЕ запускать тесты напрямую.**
- Каждый шаг выполняется субагентом через инструмент `Task`.
- Ассистент — только координатор: «Если ты собрался сделать что-либо, кроме вызова `Task`, — СТОП».

Дальше — блок **«MANDATORY: Read and follow the skill»**: прочитать `.cursor/skills/refactor-workflow/SKILL.md` инструментом Read **прямо сейчас, до всего остального**; исполнить скилл в точности, вызывая `Task(subagent_type=...)` на каждом шаге; **не пропускать, не сокращать и не «пересказывать» шаги скилла**.

## Запускаемый скилл и цепочка агентов

Команда — тонкая обёртка над скиллом **`refactor-workflow`** (`.cursor/skills/refactor-workflow/SKILL.md`). Цепочка:

`/refactor` → скилл `refactor-workflow` → определение скоупа → проверка предусловия «тесты существуют» → **senior-reviewer** (только анализ) → **refactor** (применяет правки) → **test-runner** (линтер + тесты) → при падениях **debugger** (до 3 попыток) → **documenter** (отчёт о рефакторинге).

Общий лимит скилла: **максимум 3 попытки на этап**; при превышении — пауза и отчёт пользователю.

### Пересказ скилла `refactor-workflow`

**Шаг 1 — Define Scope.** Извлечь скоуп из ввода пользователя (варианты выше) до вызова любых агентов; при неясности — спросить.

**Шаг 2 — Pre-condition Check: тесты должны существовать (CRITICAL).** Перед рефакторингом проверить наличие тестов на целевой код. Если тестов нет: предупредить пользователя («Рефакторинг без тестов рискован. Рекомендуется: сначала `/implement` для добавления тестов, потом `/refactor`»), спросить «Продолжить всё равно? (рискованно) или сначала добавить тесты?»; при продолжении — действовать с повышенной осторожностью, без смены поведения.

**Шаг 3 — Analysis Phase (senior-reviewer).** Вызвать senior-reviewer с явной инструкцией **только анализировать, не чинить**. Запросить: запахи кода с локациями (файл + примерный диапазон строк); рекомендуемый тип рефакторинга для каждого запаха; приоритет High/Medium/Low; зависимости (какие запахи блокируют другие). Таблица запахов из скилла: длинная функция (>30 строк) → Extract Function; God-класс (>300 строк) → Extract Class; дублирование → Extract + Reuse; глубокая вложенность (>3 уровней) → Guard Clauses / Early Return; feature envy → Move Method; data clump (3+ повторяющихся параметра) → Extract Object; primitive obsession → Value Objects; switch по типу → Polymorphism / Strategy; shotgun surgery → Move + Consolidate. Ожидаемый вывод — структурированный список целей «Target N — [приоритет] запах: файл, строки, описание, рекомендация».

**Шаг 4 — Refactoring Phase (агент refactor).** Передать ему полный вывод анализа. Ключевые инструкции: полный список целей от senior-reviewer; исходный скоуп/файлы; «применяй рефакторинги в порядке приоритета»; «остановись и доложи, если какой-то рефакторинг потребует смены поведения»; «НЕ добавлять новые фичи, новые тесты, НЕ менять публичные интерфейсы». Что должен делать агент: прочитать скилл `code-quality-standards`; применять рефакторинги маленькими шагами; после каждого шага проверять, что код компилируется без явных поломок; отчитываться в формате «до/после» по каждому изменению.

**Шаг 5 — Verification Phase (test-runner).** Проверить, что ничего не сломалось: линтер на всех изменённых файлах; полный набор тестов (или связанные с изменёнными файлами, если так быстрее); подтвердить отсутствие новых падений относительно состояния до рефакторинга. При падении тестов: вызвать debugger с указанием, какой тест упал и какой рефакторинг это вызвал, с ограничением: **«Почини падение теста, НЕ отменяя рефакторинг. Рефакторинг был корректным — вероятно, изменился путь импорта, переименован символ или перемещена функция, и тесты нужно обновить»**; перезапустить test-runner; максимум 3 попытки; если всё ещё падает — пауза и полный отчёт пользователю.

**Шаг 6 — Documentation Phase (documenter).** После успешной проверки задокументировать сессию: отчёт о рефакторинге с датой, скоупом, триггером (`/refactor`); секция «Changes Applied» (что извлечено/перемещено, метрики «до/после»); секция «Metrics» (сколько функций извлечено, сколько дублей убрано, сколько файлов затронуто, тесты «12/12 passing — без регрессий»); секция «Remaining Issues» — запахи, которые senior-reviewer пометил, но они вышли за скоуп.

**Retry Logic:** `test-runner FAIL → debugger (чинит импорты/символы, не логику) → test-runner`, максимум 3 попытки; если всё ещё падает — отчёт пользователю (что рефакторилось, какой тест падает, что пытался сделать debugger) и вопрос: откатить этот конкретный рефакторинг или разбираться вручную?

## Связи с другими файлами

- **Читает**: скилл `refactor-workflow` (`.cursor/skills/refactor-workflow/SKILL.md`); `git diff` при вызове без аргументов.
- **Вызывает агентов**: `senior-reviewer` → `refactor` → `test-runner` → `documenter`; при падениях — `debugger`.
- **Читаемые агентами гайдлайны**: агент `refactor` обязан прочитать скилл `code-quality-standards` (см. `skills/code-quality-standards/`).
- **Документация результата**: отчёт о рефакторинге в `ai_docs/` по путям из `config.json`.
- **Альтернативы-соседи**: `implement.md` (сначала тесты/багфиксы), `orchestrate.md` (смена дизайна/публичного API), `review.md`, `audit.md` (источник структурных находок).
