# Команда `/implement` — простой воркфлоу «код → тест → документация»

## Назначение и как вызвать

`/implement` — облегчённая команда для **одиночных задач**: запускает простой воркфлоу **Код → Тест → Документация** без фазы планирования и без отдельного этапа ревью.

Как вызвать в чате:

- `/implement <описание задачи>` — например, `/implement Create a Button component with onClick handler`;
- также срабатывает на фразы «Implement [X]» и «Create [Y] with tests and docs» (trigger-фразы из скилла).

Для каких задач предназначена: **простые одноцелевые задачи, не требующие планирования** — компонент, функция, эндпоинт, доработка в существующем файле. Примеры из скилла: создать утилитную функцию, добавить React-компонент, реализовать API-эндпоинт, добавить фичу в существующий файл.

## Когда использовать и когда НЕ использовать

**НЕ использовать** (из секции «When NOT to Use» скилла `simple-workflow`):

- **Сложные задачи** → `/orchestrate` (там есть планирование);
- **Несколько подзадач** → `/orchestrate` (декомпозиция через planner);
- **Нужны ревью/рефакторинг** → полный цикл (`/orchestrate`) или отдельно `/review` / `/refactor`.

Таблица «Key Difference from Full Cycle» из скилла:

| Simple Workflow (`/implement`) | Full Cycle (`/orchestrate`) |
|--------------------------------|------------------------------|
| Без планирования | Стартует с planner |
| Один проход | Много задач из плана |
| Без ревью | Включает code review |
| Без циклов debugger | Авто-фикс через debugger |
| Быстро и просто | Тщательно и полно |

Противопоставление другим командам: для новых фич — `/implement` или `/orchestrate`; для проверки готового кода — `/review`; для структурных улучшений — `/refactor`; для общего аудита — `/audit`.

## Главный запрет оригинала

Оригинал открывается блоком **«⛔ YOU ARE FORBIDDEN FROM DOING ANY WORK YOURSELF»**:

- **НЕ писать код. НЕ редактировать файлы. НЕ запускать тесты напрямую.**
- Каждый шаг выполняется субагентом через инструмент `Task`.
- Ассистент — только координатор: «Если ты собрался сделать что-либо, кроме вызова `Task`, — СТОП».

Дальше — блок **«MANDATORY: Read and follow the skill»**: прочитать `.cursor/skills/simple-workflow/SKILL.md` инструментом Read **прямо сейчас, до всего остального**; исполнить скилл в точности, вызывая `Task(subagent_type=...)` на каждом шаге; **не пропускать, не сокращать и не «пересказывать» шаги скилла**.

## Запускаемый скилл и цепочка агентов

Команда — тонкая обёртка над скиллом **`simple-workflow`** (`.cursor/skills/simple-workflow/SKILL.md`). Цепочка:

`/implement` → скилл `simple-workflow` → **worker → test-writer → (хук автоформатирования в фоне*) → test-runner → documenter**.

### Пересказ скилла `simple-workflow`

**Схема воркфлоу** — Code → Write Tests → (Auto-fix) → Lint + Test → Docs:

1. **Worker** создаёт код реализации.
2. **Test-Writer** пишет развёрнутые тесты на этот код (сам определяет стек).
3. **Hook** (автоматически, в фоне) исправляет форматирование (prettier, eslint --fix)*.
4. **Test-Runner** гоняет линтер и тесты, чтобы убедиться, что всё работает.
5. **Documenter** создаёт документацию по настроенному пути документации.

Все шаги агентов видны в одном чате; хук работает в фоне*.

**Important Rules скилла:**

1. **Sequential execution** — дожидаться завершения каждого агента перед вызовом следующего.
2. **Always run all four steps** — всегда выполнять все четыре шага: worker → test-writer → test-runner → documenter.
3. **Same chat** — всё происходит в текущем разговоре, видимо пользователю.
4. **Pass context forward** — сообщать каждому агенту, что сделал предыдущий.

**Code Pattern** (псевдокод координации): шаг 1 — вызвать worker с описанием задачи, дождаться, извлечь созданные файлы; шаг 2 — вызвать test-writer («напиши тесты для: [список из шага 1]»); шаг 3 — вызвать test-runner («прогони тесты для файлов: [список из шагов 1–2]»), проверить, что тесты прошли; шаг 4 — вызвать documenter («задокументируй реализацию: [детали из шага 1]»), собрать финальную сводку.

**Benefits (преимущества):** быстро для простых задач; всегда пишутся тесты (test-writer); всегда проверяется, что тесты зелёные (test-runner); всегда создаётся документация; всё видно в одном чате; нет накладных расходов на планирование.

*Примечание: в оригинале хук упоминается, но в текущем hooks.json он не настроен — см. hooks.json.md*
