# Команда `/orchestrate` — полный цикл разработки

## Назначение и как вызвать

`/orchestrate` — самая «тяжёлая» команда системы: запускает **полный цикл разработки** от планирования до документации. Самый полный воркфлоу из пяти: **План → цикл задач (Код → Тест → Ревью) → Документация**.

Как вызвать в чате:

- `/orchestrate <описание задачи>` — например, `/orchestrate Build user authentication with email/password and OAuth`;
- также срабатывает на фразы «Orchestrate [X]» и «Full implementation of [Y]» (это trigger-фразы из скилла).

Для каких задач предназначена: **сложные фичи и системы из нескольких модулей**, где нужна декомпозиция на подзадачи. Примеры из скилла: система аутентификации целиком, админ-дашборд с CRUD, интеграция платёжки, миграция схемы БД, рефакторинг крупного модуля с тестами.

## Когда использовать и когда НЕ использовать

Сравнение с `/implement` взято из таблицы «When to Use This vs Simple Workflow» в скилле `orchestration`:

| `/implement` (простая) | `/orchestrate` (эта команда) |
|------------------------|------------------------------|
| Один компонент | Полноценная фича |
| Изменение одного файла | Несколько модулей |
| Планирование не нужно | Нужна декомпозиция |
| Быстрая задача | Комплексный проект |

**Плохие кандидаты для `/orchestrate`** (используй `/implement`): добавить одну функцию, починить простой баг, создать один компонент, обновить один файл. От других команд: для ревью существующего кода — `/review`, для структурных улучшений без смены поведения — `/refactor`, для общей проверки здоровья проекта — `/audit`.

## Главный запрет оригинала

Оригинал открывается блоком **«⛔ YOU ARE FORBIDDEN FROM DOING ANY WORK YOURSELF»**:

- **НЕ писать код. НЕ редактировать файлы. НЕ планировать и не проектировать без субагента.**
- Каждый шаг выполняется субагентом через инструмент `Task`.
- Ассистент — только координатор: «Если ты собрался сделать что-либо, кроме вызова `Task`, — СТОП».

Дальше — блок **«MANDATORY: Read and follow the skill»**: прочитать `.cursor/skills/orchestration/SKILL.md` инструментом Read **прямо сейчас, до всего остального**; исполнить скилл в точности, вызывая `Task(subagent_type=...)` на каждом шаге; **не пропускать, не сокращать и не «пересказывать» шаги скилла**.

## Запускаемый скилл и цепочка агентов

Команда — тонкая обёртка над скиллом **`orchestration`** (`.cursor/skills/orchestration/SKILL.md`). Цепочка:

`/orchestrate` → скилл `orchestration` → **planner** → цикл по задачам: **worker → test-writer → test-runner → reviewer** (с циклами авто-исправления через **debugger**, до 3 попыток на этап) → **documenter**.

### Пересказ скилла `orchestration`

**Фаза 1 — Планирование.** Вызвать planner с полным описанием задачи. Planner создаёт workspace `.cursor/workspace/active/orch-{id}/`, файл плана `plan.md` (или использует файл пользователя) и метаданные `progress.json`, `tasks.json`, `links.json`; возвращает ID оркестрации.

**Фаза 2 — Загрузка оркестрации.** Прочитать `.cursor/config.json` (путь workspace), загрузить состояние: `progress.json`, `tasks.json`, `links.json`; прочитать план по ссылке `links.plan` и извлечь ID задач.

**Фаза 3 — Цикл задач (CRITICAL: обойти ВСЕ задачи).** Перед стартом задачи: пропустить уже завершённые; перевести статус `pending → in-progress` в `tasks.json`; пометить задачу «🔄 In Progress» в плане; обновить `progress.json`. Затем шаги задачи:

1. **Implementation** — worker реализует подзадачу (в скобках: хук в фоне авто-чинит форматирование*).
2. **Test Creation** — test-writer пишет тесты (сам определяет стек, следует конвенциям проекта).
3. **Linting + Testing + Verification** — test-runner проверяет линтер, тесты и критерии приёмки; при провале — debugger чинит, test-runner перезапускается, максимум 3 попытки.
4. **Code Review** — reviewer проверяет качество; при замечаниях — debugger улучшает код, reviewer перезапускается, максимум 3 попытки.
5. **Update Task Status** — статус `in-progress → completed` с `filesChanged`, счётчиками тестов; отметка «✅ Completed» в плане; инкремент `tasksCompleted` в `progress.json`.

**Фаза 4 — Финализация.** Статус `documenting`; вызов documenter для финального отчёта (получает ID оркестрации, план, состояние задач); ссылка на отчёт в `links.json`; статус `completed` с `reportFile`; перенос папки из `workspace/active/` в `workspace/completed/`.

**Важные правила скилла:**

- **Sequential Execution** — дожидаться завершения каждого агента перед вызовом следующего; передавать контекст дальше; трекать состояние по всему воркфлоу.
- **Error Handling** — авто-retry через debugger; максимум 3 попытки на этап (тесты и ревью); при исчерпании — отчёт пользователю и вопрос, как продолжать.
- **Task Limits** — рекомендуемый максимум **10 задач на цикл**; если planner создал больше — выполнить первые 10, отчитаться и спросить, продолжать ли; следить за контекстным окном, при приближении к лимиту — сохранить прогресс и спросить пользователя.
- **Task Tracking** — показывать прогресс после каждой задачи («Task 3/7»), оценку оставшихся задач, финальный итог по всей работе.
- **Context Management** — каждый агент получает контекст от предыдущих; debugger — конкретные ошибки; documenter — полную картину изменений.

**Ключевые фичи:** автоматическое планирование; тесты на каждую задачу; авто-исправление через debugger; ворота качества test-writer → test-runner → reviewer; трекинг прогресса; полная документация в конце.

**Критерии успеха:** все задачи реализованы, тесты зелёные, ревью пройдено, критерии приёмки подтверждены test-runner'ом, документация создана.

**Примечания скилла:** скилл заменяет оркестрацию на хуках («replaces hook-based orchestration»); всё происходит в одном чате на глазах у пользователя; пользователь может вмешаться в любой момент; debugger вызывается только при реальных ошибках; лимит в 3 попытки предотвращает бесконечные циклы.

*Примечание: в оригинале хук упоминается, но в текущем hooks.json он не настроен — см. hooks.json.md*
