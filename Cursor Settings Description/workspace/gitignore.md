# `workspace/.gitignore` — что из состояния оркестраций не попадает в git

## Назначение файла в системе

Локальный `.gitignore`, который действует **только внутри папки `.cursor/workspace/`** (правила `.gitignore` применяются к своей папке и всем вложенным). Его задача — отрезать от репозитория **временное служебное состояние оркестраций**, оставив под git только саму «рамку» папки.

Почему это важно: `.cursor/workspace/` — рабочая зона агентов. Во время оркестрации сюда постоянно пишутся и переписываются `progress.json`, `tasks.json`, `links.json`, `plan.md` — десятки коммитоопасных изменений в минуту. Если бы это состояние попадало в git, история репозитория превратилась бы в мусор из служебных JSON-диффов, а параллельные оркестрации на разных машинах — в источник конфликтов слияния.

## Полный текст оригинала

```gitignore
# Ignore all workspace content (temporary state)
active/
completed/
failed/

# Keep this README
!README.md
!.gitignore
```

## Построчный разбор

### Что игнорируется и почему

| Правило | Что закрывает | Почему это не должно попадать в git |
|---------|---------------|--------------------------------------|
| `active/` | Папки идущих оркестраций `active/orch-{id}/` с живым состоянием: `plan.md`, `progress.json`, `tasks.json`, `links.json`. | Это **временное, постоянно меняющееся состояние**. Статус задачи меняется `pending → in-progress → completed` несколько раз за сессию; каждый такой апдейт — потенциальный коммит-шум. Ценность папки умирает вместе с завершением оркестрации. |
| `completed/` | Папки завершённых оркестраций, перемещённые из `active/` при финализации. | Архив до автоочистки. По настройкам `config.json` (`cleanup.autoCleanCompleted: true`, `cleanupAfterDays: 7`) эти папки живут неделю и удаляются. Всё долговременно ценное из них (план, отчёт) уже сохранено в `ai_docs/` — коммитить временный архив бессмысленно. |
| `failed/` | Папки упавших оркестраций (по `config.json`, `cleanup.keepFailed: true` они не удаляются автоматически). | Отладочный материал для разбора сбоев. В git он не нужен: это локальные «улики» конкретной машины и конкретного запуска, а не часть истории проекта. |

Общий принцип: игнорируется **состояние процесса** (кто, что, на каком этапе делает), а **результат процесса** (планы, отчёты, документация) попадает в git через `ai_docs/` — она лежит вне workspace и этим `.gitignore` не затрагивается.

### Что оставлено в git

| Правило | Что возвращает под git | Зачем |
|---------|------------------------|-------|
| `!README.md` | `README.md` внутри `.cursor/workspace/`. | Строка комментария «Keep this README» — README объясняет назначение папки тому, кто заглянет внутрь (человеку или агенту). Восклицательный знак отменяет игнорирование для конкретного файла: без `!README.md` он попал бы под общий забор служебного содержимого. |
| `!.gitignore` | Сам этот `.gitignore`. | Классический приём «папка под git, содержимое — нет»: благодаря тому, что сам `.gitignore` закоммичен, структура игнорирования воспроизводится у всех, кто клонирует репозиторий. Иначе каждому пришлось бы настраивать исключения руками. |

Синтаксис `!` — это **negation** (отрицание) в формате gitignore: правило с `!` отменяет действие более раннего правила для совпавшего пути. Порядок строк важен: сначала «запретить всё служебное», потом «вернуть исключения».

## Что изменится при правке

| Правка | Эффект |
|--------|--------|
| Удалить строку `active/` | Живое состояние идущих оркестраций начнёт светиться в `git status` при каждом запуске `/orchestrate`. Практически гарантированный мусор в коммитах. |
| Удалить `!README.md` | Если/когда в workspace появится README, он будет игнорироваться вместе со всем остальным. |
| Удалить `!.gitignore` | Сам файл перестанет попадать в репозиторий → у других участников клона правила игнорирования пропадут → их git начнёт тащить в индекс `active/`, `completed/`, `failed/`. Ломать не рекомендуется. |
| Добавить, например, `*.log` | Дополнительное исключение для возможных лог-файлов внутри workspace — безопасная правка, действует только в этой папке. |

## Связи с другими файлами

- **`config.json`** (описание — `../config.json.md` в этом справочнике): блок `workspace.path` указывает на эту папку, а блок `cleanup` (`autoCleanCompleted`, `cleanupAfterDays: 7`, `keepFailed`) определяет жизненный цикл игнорируемых папок — именно конфиг объясняет, почему `completed/` временный, а `failed/` хранится вечно.
- **Скилл `orchestration`**: его Phase 1 и Phase 4 создают и перемещают папки `active/orch-{id}/` → `completed/orch-{id}/` — то есть порождают именно то содержимое, которое этот `.gitignore` прячет.
- **Скилл `task-management`**: форматы `progress.json` / `tasks.json` / `links.json`, лежащих внутри игнорируемых папок.
- **Агент `planner`**: создаёт `active/orch-{id}/` и наполняет его файлами состояния.
- **Агент `documenter`**: пишет финальные отчёты не сюда, а в `ai_docs/` — поэтому результат работы в git попадает, а процесс — нет.
- **Корневой `.gitignore` проекта** (если появится): правила отсюда дополняют его, а не заменяют; область действия этого файла — только `.cursor/workspace/`.
