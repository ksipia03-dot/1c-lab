> ⚠️ Это **описание для справки**, а не рабочий конфиг. Файл ничего не запускает и ни на что не влияет. Рабочая версия лежит в `.cursor/config.json` — править поведение нужно только там.

# `config.json` — конфигурация workspace и документации

## Назначение файла в системе

Центральный конфигурационный файл системы оркестрации. Это **не настройка самого редактора Cursor** (те хранятся в settings.json), а **проектный конфиг**, который придуман внутри этой системы агентов и читается скиллами и агентами во время работы.

Файл отвечает на два вопроса:

1. **Где и как долго хранить временное состояние оркестраций** (блок `workspace`) — рабочие папки `active/`, `completed/`, `failed/` с `plan.md`, `progress.json`, `tasks.json`, `links.json`.
2. **Куда складывать постоянную документацию проекта** (блок `documentation`) — 11 путей внутри `ai_docs/` и переключатели для каждого типа документов.

Важный нюанс чтения: скилл `orchestration` читает конфиг с запасным вариантом — `config = readJSON(".cursor/config.json") || defaultConfig`. То есть если файл удалить или он окажется битым, система не упадёт, а продолжит работать на значениях по умолчанию, зашитых в скиллы. Конфиг — это слой настройки поверх встроенных дефолтов, а не обязательный файл.

## Блок `workspace` — временное состояние оркестраций

| Ключ | Значение | Что означает и что изменится при правке |
|------|----------|------------------------------------------|
| `path` | `.cursor/workspace` | Корневая папка, где planner создаёт рабочие директории оркестраций (`active/orch-{id}/`, `completed/orch-{id}/`, `failed/orch-{id}/`). Скилл `orchestration` читает именно этот ключ в Phase 2 (`workspacePath = config.workspace.path`). **Если изменить** — например на `.cursor/run` — все новые оркестрации будут создаваться уже там; старые папки сами не переедут, их нужно переносить руками, иначе «продолжить прерванную оркестрацию» через `findLatestActive()` не найдёт старые записи. |
| `cleanup.autoCleanCompleted` | `true` | Автоматически удалять папки завершённых оркестраций из `completed/`. Смысл: после финализации вся ценная информация (план, отчёт) уже лежит в `ai_docs/`, а служебные `progress.json`/`tasks.json` — мусор. **Если поставить `false`** — папки завершённых оркестраций будут копиться вечно: удобно для расследований «как именно шла оркестрация», но забивает диск мелкими JSON-файлами. |
| `cleanup.cleanupAfterDays` | `7` | Через сколько дней после завершения удалять папку из `completed/`. Работает только вместе с `autoCleanCompleted: true`. **Если увеличить** (например до `30`) — месяц можно будет заглянуть внутрь завершённой оркестрации; **если уменьшить** (например до `1`) — workspace очищается почти сразу, отладочный след почти не остаётся. |
| `cleanup.keepFailed` | `true` | **Не** удалять папки упавших оркестраций (`failed/`). Это защита от потери улик: если цикл вылетел по ошибке или исчерпал 3 попытки авто-фикса, папка со статусами остаётся для разбора. **Если поставить `false`** — упавшие оркестрации будут чиститься наравне с завершёнными, и разобрать причину сбоя задним числом станет невозможно. Менять на `false` не рекомендуется. |

## Блок `documentation` — пути и переключатели `ai_docs/`

### Подблок `paths` — 11 путей

| Ключ | Путь | Что туда пишется |
|------|------|-------------------|
| `root` | `ai_docs` | Корень всей проектной документации. Остальные пути логически вложены в него (хотя технически каждый путь полный и самостоятельный — вложенность соблюдается по договорённости, а не вычисляется из `root`). |
| `plans` | `ai_docs/develop/plans` | Планы оркестраций, которые создаёт planner (на них ссылается `links.json` в workspace). |
| `reports` | `ai_docs/develop/reports` | Финальные отчёты оркестраций от documenter'а. |
| `issues` | `ai_docs/develop/issues` | Журнал некритичных проблем, которые агенты фиксируют по ходу работы (см. скилл `task-management`). |
| `architecture` | `ai_docs/develop/architecture` | Описания архитектурных решений и структуры модулей. |
| `features` | `ai_docs/develop/features` | Документация по отдельным фичам после их реализации. |
| `api` | `ai_docs/develop/api` | Описание API-эндпоинтов проекта. |
| `components` | `ai_docs/develop/components` | Описание компонентов (UI и не только). |
| `design` | `ai_docs/design` | Дизайн-документы. Обратите внимание: лежит **не** в `develop/`, а на уровень выше — дизайн считается отдельной дисциплиной. |
| `changelog` | `ai_docs/changelog` | История изменений проекта. Тоже на верхнем уровне `ai_docs/`, вне `develop/`. |
| `audits` | `ai_docs/develop/audits` | Консолидированные отчёты аудитов (команда `/audit`, скилл `audit-workflow`). |

**Что изменится при правке пути**: новые документы соответствующего типа будут создаваться по новому адресу. Старые файлы не переносятся — ссылки из существующих `links.json` и отчётов на старые места останутся рабочими только если старые файлы оставить на месте. Поэтому пути лучше задать один раз в начале проекта и дальше не трогать.

### Подблок `enabled` — 10 флагов

Все флаги сейчас `true` — включены все типы документации. Каждый флаг соответствует одноимённому ключу из `paths` (кроме `root` — корень отключить нельзя, он не документ, а точка монтирования).

Смысл флага: **должен ли documenter (и другие агенты) создавать документы этого типа**. Если поставить, например, `"api": false` — по завершении оркестраций описание API писаться не будет, даже если код содержал эндпоинты.

**Два способа отключения** (подсказка зашита прямо в поле `comment` оригинала): поставить флаг в `false` **или** обнулить путь (`"api": null`). Оба варианта равнозначны по эффекту; флаг нагляднее, `null` явнее показывает «пути не существует».

### Поле `comment`

```json
"comment": "Customize paths for your project. Set 'enabled' to false or path to null to disable specific documentation types"
```

Поле-подсказка для человека, читающего конфиг. Никто из агентов и скиллов его не читает и не исполняет — это чисто документирующий комментарий внутри JSON (у JSON нет родного синтаксиса комментариев, поэтому он оформлен как обычное строковое поле). Перевод: «Настройте пути под свой проект. Чтобы отключить конкретный тип документации, поставьте `enabled` в `false` или путь в `null`». Можно редактировать или удалять без последствий для системы.

## Кто читает этот конфиг

| Читатель | Что берёт из конфига |
|----------|----------------------|
| Скилл `orchestration` | `workspace.path` (Phase 2 — загрузка оркестрации), пути `plans`/`reports` при финализации. |
| Скилл `task-management` | Пути документации (куда писать issues), структуру workspace. |
| Скилл `docs` | Всю карту `documentation.paths` — это его предметная область: скилл объясняет структуру `ai_docs/`. |
| Агент `planner` | `workspace.path` (создаёт `active/orch-{id}/`) и путь `plans` (куда сохранить план). |
| Агент `documenter` | Все включённые пути `documentation.paths` — пишет отчёты, фичи, архитектуру, changelog и т.д. |

Остальные агенты (worker, test-writer, test-runner, debugger, reviewer и др.) конфиг напрямую не читают — они получают нужные пути через контекст от координатора.

## Связи с другими файлами

- **Читается скиллами**: `orchestration` (путь workspace и пути планов/отчётов), `task-management` (пути issues, форматы файлов состояния), `docs` (структура `ai_docs/` целиком).
- **Читается агентами**: `planner` (создание workspace и плана), `documenter` (запись всех типов документов).
- **Определяет содержимое папки** `.cursor/workspace/` — см. описание `workspace/gitignore.md`: именно из-за того, что `active/`, `completed/`, `failed/` — временное состояние, они и исключены из git.
- **Определяет структуру** `ai_docs/` — корневой папки проектной документации.
- **Зеркало-описание в этом справочнике**: `skills/orchestration/SKILL.md`, `skills/task-management/SKILL.md`, `skills/docs/SKILL.md`, `agents/planner.md`, `agents/documenter.md`, `workspace/gitignore.md`.
- **Не связан** с `hooks.json`: хуки — отдельный механизм (события редактора), конфиг им не нужен.
