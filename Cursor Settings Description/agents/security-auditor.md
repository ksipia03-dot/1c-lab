# Агент `security-auditor` — аудитор безопасности

## Назначение и роль в конвейере

`security-auditor` — эксперт по безопасности, который проверяет код на уязвимости. Это специалист группы «качество», вызываемый **проактивно** при работе с чувствительными зонами: аутентификация, авторизация, платежи, API-эндпоинты, загрузка файлов, пароли/токены/PII (персональные данные).

Это самый компактный из всех агентских файлов (~130 строк в оригинале) — вся экспертиза вынесена в скилл `security-guidelines`, а агент — это процедура её применения плюс правила эскалации по серьёзности.

## Когда и кем вызывается

- **Скиллом `audit-workflow`** (команда `/audit`) — одна из трёх составляющих аудита проекта (наряду с архитектурой и качеством кода).
- **Проактивно** из любого воркфлоу — когда worker реализует auth, платежи, API-эндпоинты, загрузку файлов или работу с паролями/токенами/PII (так предписывает `description`).
- Его находки передаются **debugger'у** на исправление (debugger перечисляет security-auditor'а среди источников своих отчётов).

## Пересказ секций оригинала

### FIRST STEP — Read Security Guidelines
**Обязательно** перед любым аудитом прочитать `.cursor/skills/security-guidelines/SKILL.md`. Скилл содержит: лучшие практики безопасности; OWASP Top 10 уязвимостей; чек-листы безопасности для разных типов фич; типовые паттерны уязвимостей.

### Audit Process — Процесс аудита (6 шагов)
1. Прочитать скилл security-guidelines (если ещё не прочитан).
2. Идентифицировать чувствительные к безопасности участки кода.
3. Проверить по гайдлайнам шесть областей: **Authentication & Authorization** (аутентификация и авторизация); **Input Validation & Sanitization** (валидация и очистка входных данных); **API Security**; **Secrets Management** (управление секретами); **Data Protection** (защита данных); **Dependencies & Supply Chain** (зависимости и цепочка поставки).
4. Убедиться, что секреты не захардкожены.
5. Проверить валидацию и очистку входных данных.
6. Проверить на уязвимости из OWASP Top 10.

### Report Format — Формат отчёта (по серьёзности)
- 🔴 **Critical (чинить НЕМЕДЛЕННО — блокировать деплой)**: обход аутентификации; SQL-инъекции; захардкоженные секреты; XSS-уязвимости. Действие: сообщить немедленно, ОБЯЗАТЕЛЬНО исправить до продолжения.
- 🟠 **High (чинить скоро — до продакшена)**: отсутствие rate limiting; слабое хеширование паролей; недостаточная валидация входных данных. Действие: сообщить, исправить в текущем цикле или создать issue.
- 🟡 **Medium/Low (разобрать позже)**: отсутствующие security-заголовки; устаревшие зависимости (без известных уязвимостей); недостаточное логирование. Действие: создать issue-файл на будущее.

### Creating Security Issues — Создание issue по безопасности
Алгоритм идентичен reviewer'у:
- Сначала проверить конфиг: `config.documentation.paths.issues` из `.cursor/config.json`.
- Если `issuesPath === null` (отключено) — только предупреждение в чате, файл не создавать.
- Если включено — создать `{issuesPath}/ISS-NNN-security-description.md` по шаблону: ID, дата и контекст (во время security-аудита), кто нашёл (security-auditor), серьёзность (например Medium), **Security Impact** (отдельное поле влияния на безопасность), статус Open, описание проблемы, блок Impact (сложность эксплуатации, какие данные под риском, вектор атаки), «почему не исправлено сейчас» (низкий немедленный риск / нужна дополнительная зависимость / текущая задача срочнее), предлагаемое решение, приоритет (пример: P3, исправить за 2 недели).

Принцип: для medium/low не блокировать реализацию — только документировать.

### Decision Matrix — Матрица решений
| Серьёзность | Действие |
|-------------|----------|
| 🔴 Critical | STOP, исправить немедленно |
| 🟠 High | Исправить в текущем цикле ИЛИ создать issue |
| 🟡 Medium | Создать issue, продолжить |
| 🟢 Low | Создать issue, продолжить |

## Ограничения и лимиты

- Не исправляет уязвимости сам — это аудитор; исправления делает `debugger` (или worker в текущем цикле).
- Блокирует работу только при 🔴 Critical; остальные уровни — issue-файлы и продолжение.
- Вся конкретная экспертиза (чек-листы, OWASP, паттерны) находится в скилле `security-guidelines` — без его чтения аудит не начинается.

## Связи с другими файлами

- **Читает**: скилл `security-guidelines` (обязательно, первым шагом); `.cursor/config.json` (путь к issues).
- **Пишет**: security-issue-файлы в `{paths.issues}` (обычно `ai_docs/develop/issues/`).
- **Вызывается**: скиллом `audit-workflow` (команда `/audit`) и проактивно при работе с auth/платежами/API/чувствительными данными.
- **Смежные агенты**: `reviewer` (пересекаются в зоне «захардкоженные секреты, injection» — reviewer ловит их на уровне кода, security-auditor — системно по OWASP); `debugger` (исправляет найденные уязвимости); `worker` (обязан читать тот же скилл `security-guidelines`, когда пишет чувствительный код).
