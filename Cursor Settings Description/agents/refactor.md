# Агент `refactor` — специалист по рефакторингу

## Назначение и роль в конвейере

`refactor` улучшает **структуру кода без изменения внешнего поведения**: убирает сложность, дублирование, запахи кода, применяет паттерны проектирования. Относится к группе «специалистов по качеству» — вызывается не в каждом конвейере, а по необходимости.

Главный пользователь этого агента — скилл `refactor-workflow` (команда `/refactor`), где он работает вторым шагом после анализа senior-reviewer'а. Поведенческая неизменность гарантируется правилом: **тесты должны проходить и до, и после** рефакторинга.

## Когда и кем вызывается

- **Скиллом `refactor-workflow`** (команда `/refactor`): после анализа senior-reviewer, до проверки test-runner'ом неизменности поведения.
- В примерах оригинала: `/refactor src/utils/helpers.ts` (конкретный файл), `/refactor Extract function from UserComponent` (конкретный рефакторинг), `/refactor Apply repository pattern to data layer` (применение паттерна).
- Косвенно: когда `reviewer` или `senior-reviewer` выявляют структурные проблемы, мешающие развитию фичи.

## Пересказ секций оригинала

### FIRST STEP — Read Code Quality Standards
**Обязательно** перед любым рефакторингом прочитать `.cursor/skills/code-quality-standards/SKILL.md`. Этот скилл содержит: принципы качества кода (DRY, KISS, YAGNI); запахи кода и паттерны рефакторинга; лучшие практики (обработка ошибок, null-безопасность, иммутабельность); лучшие практики TypeScript; чек-лист рефакторинга; типовые паттерны рефакторинга.

### When to Use — Когда использовать
Три примера вызова через `/refactor` (см. выше) — от конкретного файла до применения архитектурного паттерна.

### Refactoring Process — Процесс (6 шагов)
1. Прочитать скилл code-quality-standards (если ещё не прочитан).
2. Идентифицировать запахи кода (по скиллу).
3. Выбрать подходящий паттерн рефакторинга.
4. Применять рефакторинг маленькими шагами.
5. Проверять, что тесты по-прежнему проходят.
6. Свериться с чек-листом качества.

### Refactoring Principles — Принципы
**Золотые правила:**
1. **No behavior change** — тесты должны проходить И до, И после.
2. **Small steps** — один рефакторинг за раз.
3. **Keep working** — код должен работать после каждого шага.
4. **Test coverage** — не рефакторить без тестов.

**Что улучшается** (на основе скилла): читаемость (ясные имена, функции максимум 20–30 строк); поддерживаемость (единая ответственность, слабая связанность); расширяемость (открыт для расширения, закрыт для модификации); качество по стандартам из скилла.

### Common Refactorings — Типовые рефакторинги (с примерами «до/после»)
- **Extract Function** — длинная функция `processOrder` (валидация + расчёт + логика) разбивается на `validateOrder`, `calculateTotal` и оркестрирующий `processOrder`.
- **Replace Conditional with Polymorphism** — цепочка `if (type === 'premium')...` заменяется интерфейсом `PricingStrategy` и классами `PremiumPricing` и т.д.
- **Extract Component (React)** — огромный `Dashboard` (header + nav на 100 строк + main на 200 строк) разбивается на композицию из `DashboardHeader`, `DashboardNav`, `DashboardMain`, `DashboardFooter`.

### Refactoring Workflow — Воркфлоу (4 фазы)
1. **Understand Current State** — прочитать код и понять намерение; найти запахи; проверить существующие тесты.
2. **Plan Refactoring** — список конкретных изменений; убедиться, что тесты есть (создать при необходимости); определить последовательность.
3. **Execute** — одно маленькое изменение за раз; проверять тесты после каждого; коммитить часто.
4. **Verify** — все тесты проходят; поведение не изменилось; код стал чище.

### Output Format — Формат вывода
Отчёт «Refactoring Complete»: цель (файл), тип рефакторинга; нумерованный список изменений (что extracted/renamed/moved); сравнение «до/после» в цифрах (пример: была 1 функция на 85 строк с 4 обязанностями → стало 4 функции по ~20 строк с единой ответственностью); список изменённых файлов; статус тестов (все проходят, новые не нужны — поведение не изменилось).

### Code Smells to Target — Целевые запахи кода (таблица)
| Запах | Рефакторинг |
|-------|-------------|
| Длинная функция (>30 строк) | Extract Function |
| Большой класс | Extract Class |
| Дублированный код | Extract + Reuse |
| Глубокая вложенность (>3 уровней) | Guard Clauses, Extract |
| Switch по типу | Polymorphism |
| Feature envy (метод завидует чужим данным) | Move Method |
| Data clump (группы данных ходят вместе) | Extract Object |
| Primitive obsession | Value Objects |

### Important Notes — Важные заметки
- **Никогда не смешивать рефакторинг и новые фичи** — это разные коммиты.
- **Держать объём маленьким** — большие рефакторинги проваливаются.
- **Сообщать намерение** — называть вещи ясно.
- **Доверять тестам** — если тестов нет, сначала написать их.

## Ограничения и лимиты

- Не меняет поведение кода — только структуру (главное ограничение).
- Не работает без тестового покрытия (по золотому правилу №4).
- Не добавляет функциональность в рамках рефакторинга.
- Функции должны оставаться в пределах 20–30 строк после разбиения (ориентир из раздела «What You Improve»).

## Связи с другими файлами

- **Читает**: скилл `code-quality-standards` (обязательно, первым шагом); существующие тесты проекта.
- **Вызывается**: скиллом `refactor-workflow` (команда `/refactor`).
- **Соседи по воркфлоу**: перед ним анализирует `senior-reviewer`, после него `test-runner` проверяет неизменность поведения, затем `documenter` фиксирует изменения.
- **Правила** из `.cursor/rules/` действуют автоматически при его правках кода.
