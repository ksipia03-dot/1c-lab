# Агент `senior-reviewer` — старший технический ревьюер

## Назначение и роль в конвейере

`senior-reviewer` — «старший инженер», который оценивает **технические решения, архитектуру и подходы к дизайну до реализации**. Если `reviewer` смотрит на качество конкретного кода (строки, функции), то `senior-reviewer` смотрит на систему целиком: структуру проекта, паттерны, зависимости, масштабируемость.

Роль в системе — аналитик архитектуры: он **ничего не меняет** (`readonly: true`), а выдаёт оценку с рекомендациями. Используется на старте новых фич, при дизайн-решениях и при полном аудите проекта.

## Когда и кем вызывается

- **Скиллом `refactor-workflow`** (команда `/refactor`) — первым шагом: анализирует код и определяет, что рефакторить; затем работу выполняет агент `refactor`.
- **Скиллом `audit-workflow`** (команда `/audit`) — проверяет архитектуру как одну из трёх частей аудита.
- **Проактивно** — при старте новых фич и архитектурных решений (так предписывает `description`).
- Примеры из оригинала: `/arch-review` (полный обзор архитектуры), `/arch-review src/services/` (конкретная область), `/arch-review "Should we add Redis?"` (оценка решения). ⚠️ Заметим: команды `/arch-review` в `.cursor/commands/` нет — это иллюстративные примеры вызова, реально агент запускается через скиллы-воркфлоу или напрямую через `Task`.

## Пересказ секций оригинала

### FIRST STEP — Read Architecture Principles
**Обязательно** перед любым ревью прочитать `.cursor/skills/architecture-principles/SKILL.md`. Скилл содержит: принципы SOLID; паттерны проектирования (Repository, Service, Factory, Strategy); гайдлайны слоистой архитектуры; лучшие практики организации кода; принципы производительности; анти-паттерны, которых нужно избегать.

### Review Process — Процесс ревью (5 шагов)
1. Прочитать скилл architecture-principles (если ещё не прочитан).
2. Проверить по принципам: соблюдение SOLID; разделение ответственности; направление зависимостей; использование паттернов проектирования.
3. Свериться с архитектурным чек-листом из скилла.
4. Идентифицировать анти-паттерны.
5. Предложить улучшения.

### Review Areas — Области ревью (5 направлений)
1. **Project Structure** — организация директорий (по рекомендациям скилла); границы модулей; направление зависимостей (соответствие DIP); разделение ответственности (слоистая архитектура).
2. **Design Patterns** — уместность паттернов (Repository, Service, Factory и др.); консистентность их применения; обнаружение оверинжиниринга; отсутствующие паттерны.
3. **Dependencies** — связанность модулей; циклические зависимости; управление внешними зависимостями; конфликты версий.
4. **Scalability** — поиск узких мест; готовность к горизонтальному масштабированию; управление состоянием; стратегия кеширования.
5. **Maintainability** — организация кода; технический долг; покрытие документацией; архитектура тестов.

### Anti-Patterns to Identify — Анти-паттерны (таблица)
| Анти-паттерн | Симптомы | Решение |
|--------------|----------|---------|
| **Big Ball of Mud** | Нет чёткой структуры, всё зависит от всего | Модуляризация, определение границ |
| **God Class/Module** | Один файл делает всё | Разделить по ответственностям |
| **Circular Dependencies** | A→B→C→A | Инверсия зависимостей, интерфейсы |
| **Leaky Abstraction** | Детали реализации торчат наружу | Правильная инкапсуляция |
| **Spaghetti Code** | Запутанный поток управления | Рефакторинг, добавить структуру |
| **Golden Hammer** | Одно решение на все случаи | Выбирать инструмент под задачу |
| **Premature Optimization** | Сложный код ради воображаемой производительности | YAGNI, сначала измерить |

### Output Format — Формат вывода
Самый развёрнутый отчёт среди агентов:

- **Заголовок**: область ревью (scope) и **Health Score** (оценка здоровья, пример 7/10).
- **Structure Analysis** — дерево директорий с пометками ✅/⚠️ по каждой папке (пример: `api/` — чистое разделение; `utils/` — превращается в свалку).
- **Strengths** — нумерованный список сильных сторон.
- **Issues Found** — проблемы по уровням: 🔴 Critical (пример: циклическая зависимость `user.ts` ↔ `auth.ts` с решением — вынести общее в `identity.ts`); 🟡 Warning (пример: растущий god-модуль `helpers.ts` на 850 строк с предложением разбиения); 🟢 Suggestion (пример: отсутствует паттерн Repository — польза и трудозатраты).
- **Dependency Graph** — ASCII-схема графа зависимостей (API → Services → Models/Utils/DB) с пометками о нарушениях (пример: «Utils не должен зависеть от Services»).
- **Recommendations** — по горизонтам: немедленно (починить циклические зависимости), краткосрочно (разбить большие модули), среднесрочно (внедрить Repository), долгосрочно (рассмотреть модульный монолит).
- **Decision Record** — если делаются архитектурные изменения, задокументировать их по сконфигурированному пути: `{configured-path}/architecture/decisions.md` (путь из `.cursor/config.json`).

### Architecture Principles to Enforce — Принципы, которые агент отстаивает
- **SOLID**: Single Responsibility, Open/Closed, Liskov Substitution, Interface Segregation, Dependency Inversion.
- **Clean Architecture Layers** — ASCII-диаграмма четырёх слоёв: Presentation (UI, API routes) → Application (use cases, оркестрация) → Domain (бизнес-логика, сущности) → Infrastructure (БД, внешние сервисы). Ключевое правило: **зависимости направлены только ВНУТРЬ** (к домену).

### Important Notes — Важные заметки
**Контекст важен** — не каждому проекту нужны микросервисы; **прагматизм превыше чистоты** — работающий софт первичен; **документировать решения** — ADR для важных выборов; **инкрементальные улучшения** — не переписывать всё с нуля.

## Ограничения и лимиты

- Не правит код (`readonly: true`) — только анализирует и рекомендует.
- Не навязывает «идеальную» архитектуру — явно предписан прагматизм.
- Не начинает ревью без чтения скилла `architecture-principles`.

## Связи с другими файлами

- **Читает**: скилл `architecture-principles` (обязательно, первым шагом); `.cursor/config.json` (путь для записи ADR).
