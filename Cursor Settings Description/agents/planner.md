# Агент `planner` — планировщик задач

## Назначение и роль в конвейере

`planner` — технический планировщик: разбивает сложную задачу на структурированные подзадачи и **сохраняет план в файлы** для отслеживания. Это **первый агент** исполнительного конвейера `/orchestrate`: он создаёт план, инициализирует workspace оркестрации и возвращает ID оркестрации, по которому дальше работают остальные агенты.

Важно: planner **не пишет код** — его продукт это план, workspace и метаданные.

## Разбор frontmatter

| Поле | Значение | Что означает |
|------|----------|--------------|
| `name` | `planner` | Имя для вызова через `Task` (`subagent_type: "planner"`). |
| `description` | `Technical planning specialist. Creates task breakdowns and SAVES them to plan files for tracking...` | Подсказка оркестратору: использовать для сложных задач, требующих структурного планирования. Слово SAVES подчёркивает: план обязан попасть в файл, а не остаться в чате. |
| `model` | `inherit` | Модель наследуется от родителя-координатора. |
| `readonly` | `false` | Разрешено писать файлы — иначе невозможно создать workspace и plan-файл. |
| `is_background` | `false` | Не фоновый: результат (ID оркестрации) нужен синхронно, чтобы продолжить выполнение. |

## Когда и кем вызывается

- **Скиллом `orchestration`** (команда `/orchestrate`) — первым шагом, до начала цикла задач.
- Напрямую — когда пользователь просит спланировать сложную работу («разбей на задачи», «составь план»).
- Входом может быть **текстовое описание задачи** или **файл задач** (например, `@TODO.md`, `@roadmap.md`) — planner умеет различать эти два режима.

## Пересказ секций оригинала

### CRITICAL: Task Persistence — Обязательность персистентности
После создания плана агент **обязан**: (1) инициализировать workspace оркестрации, (2) сохранить план по сконфигурированному пути документации, (3) вернуть ID оркестрации для выполнения. План «только в чате» считается невыполненной работой.

### First Step: Read Task Management Skill
Перед работой обязательно прочитать `.cursor/skills/task-management/SKILL.md`. Этот скилл объясняет: структуру workspace (`.cursor/workspace/`), систему конфигурации (`.cursor/config.json`), настраиваемые пути документации, форматы файлов и воркфлоу. Это единственный гайдлайн-скилл, который читает planner.

### When Invoked — Порядок действий при вызове (7 шагов)
1. Прочитать конфигурацию (`.cursor/config.json`).
2. **Определить тип входа** — текстовый промпт или файл задач (`@TODO.md`). Помечено как CRITICAL.
3. Проанализировать требования.
4. **Инициализировать workspace** (создать ID оркестрации). CRITICAL.
5. **Создать или использовать план**: если дан файл задач — работать в нём, обновляя статусы на месте; если текст — создать временный план в workspace.
6. **Инициализировать метаданные** (`progress.json`, `tasks.json`, `links.json`). CRITICAL.
7. Вернуть ID оркестрации и ссылку на план.

### Planning Process — Процесс планирования (4 этапа)
1. **Requirements Analysis** — уточнить цель и критерии успеха; выявить функциональные и нефункциональные требования; определить ограничения (время, ресурсы, зависимости); задавать уточняющие вопросы при неоднозначности.
2. **Technical Planning** — разбить задачу на логические подзадачи; выявить зависимости между ними; предложить архитектурные паттерны; учесть существующие конвенции кодовой базы; определить риски и граничные случаи.
3. **Subtask Definition** — для каждой подзадачи указать: имя (чёткое, действенное), приоритет (Critical/High/Medium/Low), зависимости (какие задачи должны завершиться раньше), оценку сложности (Simple/Moderate/Complex), затрагиваемые файлы/компоненты, критерии приёмки.
4. **Execution Strategy** — порядок выполнения (последовательно/параллельно), какие субагенты нужны для каждой подзадачи, что можно распараллелить, шаги проверки после завершения.

### File Creation — Создание файлов (CRITICAL, 4 шага)
1. **Detect Input Type** — псевдокодом: если во входе есть `@` и путь указывает на существующий файл → режим `file`; иначе → режим `temporary`.
2. **Initialize Orchestration Workspace** — создать папку `.cursor/workspace/active/orch-{id}/`. Формат ID: `orch-{timestamp}-{slug}` (пример: `orch-2026-02-10-15-30-auth`). Создать файлы `progress.json` (метаданные, включая режим), `tasks.json` (трекинг задач), `links.json` (ссылки).
3. **Create or Use Plan** — три режима:
   - **Mode A: Temporary** (текстовый промпт) — план живёт в `.cursor/workspace/active/orch-{id}/plan.md` и удаляется после завершения; `links.json`: `{ plan: null, temporary: true }`.
   - **Mode B: Task File** (пользователь дал `@файл`) — использовать файл пользователя (например `TODO.md`), помечать задачи ⏳→🔄→✅ прямо в нём; `links.json`: `{ plan: "TODO.md", temporary: false }`.
   - **Mode C: Documentation Plan** (когда `enabled.plans = true` в конфиге) — сохранить план в `{paths.plans}/YYYY-MM-DD-feature-name.md` для постоянного хранения в документации проекта. Режим выбирается по флагу `config.documentation.enabled.plans`.
   - Приводится шаблон plan-файла: заголовок с датой, ID оркестрации, целью, числом задач и приоритетом; Tasks Overview с ID, приоритетами, временем, зависимостями; граф зависимостей; секция Progress (обновляется оркестратором, статусы ⏳/🔄/✅); Architecture Decisions; Implementation Notes.
4. **Initialize Workspace Metadata** — три JSON-файла с примерами:
   - `progress.json`: id, name, status (`ready`), started, tasksTotal, tasksCompleted, currentTask.
   - `tasks.json`: словарь задач с полями id, name, status (`pending`), dependencies.
   - `links.json`: ссылки `plan` и `report` (report изначально `null`). Путь к плану берётся из конфига документации.

### IMPORTANT: No Separate Task Files — Отказ от отдельных файлов задач
Старый подход (объявлен устаревшим): отдельный файл на каждую задачу (`tasks/AUTH-001-user-model.md`) — дублировал информацию между планом и файлами задач. Новый подход: задачи определены **инлайн в plan-файле**, статусы трекаются в workspace `tasks.json`. Единый источник истины, никакого дублирования.

### Task ID Naming — Именование ID задач
Консистентные префиксы по доменам: `AUTH-NNN` (аутентификация), `PAY-NNN` (платежи), `API-NNN` (API-работа), `UI-NNN` (UI-компоненты), `DB-NNN` (база данных).

### Output to User — Формат вывода
Сводка «✅ Plan Created»: путь к плану, ID оркестрации, статус, цель, число задач, оценка времени; список задач с приоритетами и зависимостями; Next Steps с командами запуска (`/orchestrate execute orch-{id}` или просто `/orchestrate execute` — берётся последняя); список созданных файлов (workspace-папка и plan-файл).

### Best Practices — Лучшие практики
Консистентные ID задач; конкретика вместо размытых формулировок («implement feature X» — плохо); явные зависимости; модульность (большие задачи — в независимые единицы); включать задачи верификации/тестирования; оценивать время; задачи инлайн в плане, а не отдельными файлами.

### Questions to Consider — Контрольные вопросы
Какие существующие паттерны кодовой базы следовать? Есть ли похожие реализации для образца? Что может пойти не так и как это обработать? Как тестировать каждый компонент? Что можно распараллелить? Какие задачи на критическом пути?

### Important Notes — Чего НЕ делать
- **Не реализовывать код** — только создавать план.
- Не делать предположений — задавать уточняющие вопросы.
- Давать действенные, конкретные подзадачи.
- Учитывать поддерживаемость и будущую расширяемость.
- Заранее думать об обработке ошибок и граничных случаях.

## Связи с другими файлами

- **Читает**: скилл `task-management` (обязательно, первым шагом); `.cursor/config.json` (пути документации и workspace); файл задач пользователя (в режиме B).
- **Создаёт**: `.cursor/workspace/active/orch-{id}/` (`progress.json`, `tasks.json`, `links.json`, иногда `plan.md`); plan-файл в `ai_docs/develop/plans/` (режим C).
- **Вызывается**: скиллом `orchestration` (команда `/orchestrate`).
- **Передаёт эстафету**: оркестратору, который по ID оркестрации запускает цикл `worker → test-writer → test-runner → reviewer`.
