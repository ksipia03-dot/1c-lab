# Скилл `security-guidelines` — стандарты безопасности

## Назначение и тип

Скилл задаёт **стандарты и лучшие практики безопасности проекта**: правила аутентификации, валидации ввода, защиты API, работы с секретами, защиты данных, фронтенд-безопасности и платформенных особенностей (GraphQL, WebSocket, SSE), плюс чек-листы и перечень OWASP Top 10.

**Тип: гайдлайн** (справочник, который читают агенты). Скилл не исполняется как сценарий — он загружается в контекст агента перед работой с чувствительным кодом.

## Когда и кем читается

- **security-auditor** — перед проведением аудита безопасности.
- **worker** — при реализации аутентификации, API-эндпоинтов или обработки чувствительных данных.
- **debugger** — при исправлении дефектов безопасности.
- **reviewer** — при проверке кода на соответствие стандартам.

## Подробное содержание оригинала

### 1. Authentication & Authorization (аутентификация и авторизация)

**✅ DO:** bcrypt/argon2 для хеширования паролей (никогда не MD5/SHA1); rate limiting на auth-эндпоинтах; безопасные сессии (httpOnly, secure cookies); CSRF-защита для операций, меняющих состояние; JWT с коротким сроком жизни (access — 15 минут, refresh — 7 дней); refresh-токены хранить зашифрованными в БД.

**❌ DON'T:** не хранить пароли открытым текстом или в обратимом шифровании; не светить user ID в URL (использовать UUID); не доверять только клиентской валидации; не писать собственную криптографию (только устоявшиеся библиотеки).

Пример из оригинала: ✅ `bcrypt.hash(password, 10)` против ❌ `crypto.createHash('md5').update(password)`.

### 2. Input Validation & Sanitization (валидация и очистка ввода)

**✅ DO:** валидировать весь пользовательский ввод на сервере; allowlists вместо denylists; санитизация HTML (DOMPurify на клиенте, sanitize-html на сервере); валидация загружаемых файлов (тип, размер, содержимое); параметризованные SQL-запросы (никакой конкатенации строк).

**❌ DON'T:** не доверять никаким клиентским данным; не использовать `eval()` или `Function()` на пользовательском вводе; не выполнять код, предоставленный пользователем.

Пример из оригинала: ✅ параметризованный запрос `WHERE email = $1` против ❌ интерполяции `WHERE email = '${email}'` (SQL-инъекция).

### 3. API Security (безопасность API)

**✅ DO:** HTTPS везде (TLS 1.2+); rate limiting (по IP и по пользователю); валидация заголовков Content-Type; корректный CORS (без `*` в проде); обобщённые сообщения об ошибках (без утечки деталей реализации); логирование событий безопасности (неудачные логины, отказы в доступе).

**❌ DON'T:** не показывать stack trace в проде; не возвращать чувствительные данные в ошибках; не использовать предсказуемые API-ключи/токены.

Пример из оригинала: ✅ `{ error: 'Invalid credentials' }` против ❌ `{ error: 'User exists but password is wrong' }` (утечка информации).

### 4. Secrets Management (управление секретами)

**✅ DO:** переменные окружения для секретов; инструменты управления секретами (AWS Secrets Manager, Vault); регулярная ротация; разные секреты для dev/staging/prod; `.env` в `.gitignore`.

**❌ DON'T:** никогда не коммитить секреты в Git; не хардкодить API-ключи в коде; не логировать секреты (пароли, токены, ключи).

Пример из оригинала: ✅ `process.env.API_KEY` против ❌ строки `"sk_live_12345abcdef"` в коде.

### 5. Data Protection (защита данных)

**✅ DO:** шифрование чувствительных данных при хранении (PII, платёжная информация); HTTPS при передаче; контроль доступа (RBAC/ABAC); минимизация сбора данных (GDPR); безопасное удаление данных.

**❌ DON'T:** не хранить чувствительные данные без необходимости; не логировать их; не делиться данными без согласия пользователя.

### 6. Dependencies & Supply Chain (зависимости и цепочка поставки)

**✅ DO:** регулярно обновлять зависимости (`npm audit` / `yarn audit`); использовать lock-файлы (package-lock.json, yarn.lock); проверять зависимости перед добавлением; Snyk или Dependabot; фиксировать версии в проде.

**❌ DON'T:** не использовать устаревшие пакеты с известными уязвимостями; не ставить пакеты из недоверенных источников; не запускать `npm install` вслепую.

### 7. Frontend Security (фронтенд-безопасность)

**✅ DO:** заголовки Content Security Policy (CSP); Subresource Integrity (SRI) для CDN-ресурсов; экранирование/санитизация пользовательского контента перед рендером; встроенная XSS-защита фреймворка (React авто-экранирует); валидация и на фронтенде, и на бэкенде; безопасное хранилище (никогда не localStorage для токенов).

**❌ DON'T:** не использовать `dangerouslySetInnerHTML` без санитизации; не хранить чувствительное в localStorage/sessionStorage; не полагаться только на клиентскую валидацию; не отключать CSP и не использовать `unsafe-inline` в проде.

Примеры из оригинала: ✅ CSP-заголовок `default-src 'self'; script-src 'self' https://trusted-cdn.com`; ✅ `DOMPurify.sanitize(userInput)`; ❌ `<div dangerouslySetInnerHTML={{ __html: userInput }} />` (риск XSS).

### 8. Modern Authentication (современная аутентификация)

**✅ DO:** OAuth 2.0 / OpenID Connect для сторонней аутентификации; PKCE для публичных клиентов (SPA, мобильные); строгая валидация redirect URI; Multi-Factor Authentication (MFA); OAuth-токены в httpOnly cookies или зашифрованные.

**❌ DON'T:** не использовать implicit flow (устарел); не раскрывать client secret во фронтенд-коде; не пропускать валидацию redirect URI; не писать собственный OAuth-сервер (использовать Auth0, Keycloak и т.п.).

Примеры из оригинала: ✅ генерация PKCE (`codeVerifier`, `codeChallenge`) и передача `code_challenge` в authorize-URL; ✅ проверка MFA: если `user.mfaEnabled && !req.session.mfaVerified` → 401 `MFA required`.

### 9. Platform-Specific Security (платформенные особенности)

**GraphQL:** ограничение глубины запросов; анализ сложности запросов; persisted queries в проде; отключить introspection в проде. Пример из оригинала: `graphql-depth-limit` с `validationRules: [depthLimit(5)]` в ApolloServer.

**WebSocket:** аутентификация при подключении и на каждое сообщение; rate limiting на соединение; валидация заголовка origin; только защищённый WebSocket (`wss://`). Пример из оригинала: при `connection` извлекается `token` из query-параметров; если `verifyToken` не прошёл — `ws.close(4401, 'Unauthorized')`.

**Server-Sent Events (SSE):** требовать аутентификацию для SSE-эндпоинтов; валидировать данные событий перед отправкой; ограничивать число соединений на пользователя.

## Security Checklist — чек-лист безопасности

Используется при реализации фич. Четыре блока из оригинала:

**Authentication Feature:**
- [ ] Пароли хешированы bcrypt/argon2
- [ ] Rate limiting на логине
- [ ] Безопасные сессии (httpOnly cookies)
- [ ] CSRF-защита включена
- [ ] Сброс пароля с безопасными токенами
- [ ] Блокировка аккаунта после неудачных попыток

**API Endpoint:**
- [ ] Валидация всех параметров
- [ ] Требуется аутентификация (если не публичный)
- [ ] Проверки авторизации для ресурсов
- [ ] Настроен rate limiting
- [ ] Корректный CORS
- [ ] Обобщённые сообщения об ошибках
- [ ] Выставлены security-заголовки (CSP, X-Frame-Options и др.)

**Database Operation:**
- [ ] Параметризованные запросы
- [ ] Защита от SQL-инъекций
- [ ] Шифрование чувствительных данных
- [ ] Контроль доступа
- [ ] Аудит-логирование

**File Upload:**
- [ ] Валидация типа файла
- [ ] Ограничения размера
- [ ] Антивирусная проверка (если применимо)
- [ ] Безопасное место хранения
- [ ] Контроль доступа к файлам

## Common Vulnerabilities — OWASP Top 10 (все 10 пунктов с профилактикой)

1. **Injection (SQL, NoSQL, Command)** — параметризованные запросы, валидация ввода, ORM.
2. **Broken Authentication** — строгая политика паролей, MFA, безопасные сессии.
3. **Sensitive Data Exposure** — шифрование при хранении/передаче, минимизация сбора.
4. **XML External Entities (XXE)** — отключить обработку внешних XML-сущностей.
5. **Broken Access Control** — deny by default, проверки на сервере, логирование доступа.
6. **Security Misconfiguration** — минимальная конфигурация, автоматическое сканирование, удаление дефолтов.
7. **Cross-Site Scripting (XSS)** — экранирование вывода, CSP-заголовки, санитизация ввода.
8. **Insecure Deserialization** — не десериализовать недоверенные данные, проверки целостности.
9. **Using Components with Known Vulnerabilities** — регулярные обновления, сканирование зависимостей, мониторинг.
10. **Insufficient Logging & Monitoring** — логирование событий безопасности, алерты, реагирование на инциденты.

## Security Testing — проверки перед деплоем (6 шагов)

1. Запустить `npm audit` / `yarn audit`.
2. Проверить отсутствие захардкоженных секретов (grep, git-secrets).
3. Протестировать потоки аутентификации/авторизации.
4. Проверить валидацию ввода.
5. Пересмотреть обработку ошибок.
6. Проверить принудительный HTTPS.
