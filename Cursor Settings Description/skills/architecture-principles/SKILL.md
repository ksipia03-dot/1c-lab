# Скилл `architecture-principles` — принципы архитектуры и паттерны

## Назначение и тип

Скилл задаёт **архитектурные стандарты и паттерны проектирования** для всего проекта: SOLID, слоистая архитектура, классические паттерны (Repository, Service, Factory, Strategy), внедрение зависимостей, обработка ошибок, управление конфигурацией, организация кода, производительность, стратегия тестирования и анти-паттерны.

**Тип: гайдлайн** (справочник). Это не сценарий: скилл никого не вызывает и ничего не исполняет. Его **читают агенты перед работой**, чтобы принимать согласованные архитектурные решения. В конце оригинала прямо сказано: скилл предназначен для консультации агентами при принятии архитектурных решений и ревью дизайна системы.

## Подробный пересказ содержимого

### Core Principles → 1. SOLID

Пять принципов SOLID, каждый с формулировкой:

- **SRP (Single Responsibility)** — один класс/модуль = одна причина для изменения; разделять concerns (данные, логика, представление). Пример из оригинала: ✅ `UserRepository.findById(id)` (только работа с БД) и `UserService.validateUser(user)` (только бизнес-логика); ❌ класс `User` с методами `save()` + `validate()` + `render()` — три причины для изменения сразу.
- **OCP (Open/Closed)** — открыт для расширения, закрыт для модификации; использовать интерфейсы, абстрактные классы, композицию.
- **LSP (Liskov Substitution)** — подтипы должны быть взаимозаменяемы с базовыми типами; не нарушать контракты родительского класса.
- **ISP (Interface Segregation)** — много специфичных интерфейсов лучше одного общего; клиенты не должны зависеть от неиспользуемых методов.
- **DIP (Dependency Inversion)** — зависеть от абстракций, а не от конкретных реализаций; высокоуровневые модули не должны зависеть от низкоуровневых.

### Core Principles → 2. Separation of Concerns (слоистая архитектура)

ASCII-диаграмма пяти слоёв (сверху вниз): **Presentation** (UI, Views) → **Application** (Use Cases, логика приложения) → **Domain** (бизнес-логика, сущности) → **Data** (доступ к данным, хранилище) → **Infrastructure** (внешние сервисы, I/O).

Правила слоёв:

- Каждый слой зависит только от слоёв ниже.
- Бизнес-логика независима от инфраструктуры.
- Каждый слой легко тестировать изолированно.
- Верхние слои зависят от абстракций, а не от реализаций.

### Core Principles → 3. Design Patterns

Четыре паттерна с псевдокодом:

- **Repository** — абстрагирует доступ к данным за интерфейсом, чтобы бизнес-логика не зависела от деталей хранилища. Пример: интерфейс `UserRepository` (`findById`, `save`, `delete`), конкретная реализация `DatabaseUserRepository` с SQL внутри, а `UserService` получает в конструктор только интерфейс (`constructor(repo: UserRepository)` — внедряется извне).
- **Service** — инкапсулирует бизнес-логику и оркестрирует зависимости. Пример `registerUser(data)`: 1) `validateRegistrationData` (guard), 2) `buildUserFromInput` (доменная логика), 3) `userRepo.save` (персистентность), 4) `notificationService.sendWelcome` (побочный эффект).
- **Factory** — создаёт объекты без хардкода конкретного класса в месте вызова. Пример: `PaymentProcessorFactory.create(type)` возвращает `StripeProcessor` для `"stripe"`, `PayPalProcessor` для `"paypal"`, иначе бросает `UnknownProcessorError`.
- **Strategy** — инкапсулирует взаимозаменяемые алгоритмы за общим интерфейсом. Пример: интерфейс `ValidationStrategy.validate(value) → bool`, реализации `EmailValidation` и `PasswordValidation` (длина ≥ 8 + заглавная буква + цифра), а `Validator` работает со стратегией, не зная какой именно.

### Core Principles → 4. Dependency Injection

Преимущества: слабая связанность (loose coupling); лёгкое тестирование (подмена реальных зависимостей моками/фейками); гибкая конфигурация. Пример: ✅ зависимости приходят снаружи (`constructor(userService, logger)` — легко тестировать и менять); ❌ зависимости создаются внутри конструктора (`new UserService()`, `new ConsoleLogger()` — хардкод, сложно тестировать и подменять).

### Core Principles → 5. Error Handling (централизованная обработка ошибок)

Использовать доменно-специфичные типы ошибок вместо общих — тогда вызывающий код может обрабатывать каждый случай явно. Пример: типы `ValidationError(message, field?)`, `NotFoundError(resource, id)`, `UnauthorizedError(message)` — все наследуют `BaseError`; центральный `ErrorHandler.handle(error)` диспетчеризует по типу: `ValidationError` → ответ 400 с указанием поля, `NotFoundError` → 404, `UnauthorizedError` → 401, иначе → 500 (детали логируются приватно, наружу не утекают).

### Core Principles → 6. Configuration Management

✅ Одно место для чтения всей конфигурации: `environment = env("APP_ENV", default="development")`, `storage.type = env("STORAGE_TYPE", default="local")`, `logging.level = env("LOG_LEVEL", default="info")`, `features.maxRetries = env("MAX_RETRIES", default=3)`. ❌ Конфигурация размазана по модулям (`storage.go` читает `STORAGE_TYPE`, `logger.py` — `LOG_LEVEL`, `retry.ts` — `MAX_RETRIES`) — сложно найти все ключи и легко забыть дефолты.

### Code Organization — организация кода

**Feature-Based Structure** (по фичам) — лучше для больших приложений с относительно независимыми фичами. Структура: `src/features/authentication/` (auth.service.ts, auth.store.ts, auth.types.ts, auth.utils.ts), `src/features/users/`, `src/features/notifications/`, плюс `src/shared/` (components, utils, types) и `src/config/`. Преимущества: фичи самодостаточны; легко находить связанный код; команды масштабируются по фичам; фичи легко добавлять и удалять.

**Layer-Based Structure** (по слоям) — лучше для маленьких приложений или когда слои важнее фич. Структура: `src/services/`, `src/repositories/`, `src/models/`, `src/utils/`, `src/types/`. Преимущества: чёткие технические границы; проще обеспечивать слоистые правила; хорошо для небольших кодовых баз; просто для понимания.

### Performance Principles — принципы производительности (4 блока)

1. **Data Access** — индексировать часто запрашиваемые данные; пагинация для больших наборов; пулинг соединений для внешних ресурсов; избегать N+1 запросов (эффективно доставать связанные данные); ленивая загрузка где уместно.
2. **Caching** — кэшировать дорогие вычисления; осмысленные стратегии инвалидации кэша; учитывать компромисс память/скорость; кэшировать на правильном слое (приложение, данные, CDN).
3. **Async Operations** — async/await для I/O; не блокировать главный поток; фоновые задачи для тяжёлой работы; очереди/стримы для развязки; искать возможности параллелизации.
4. **Resource Management** — освобождать ресурсы (соединения, файловые дескрипторы, таймеры); таймауты; пулинг объектов для дорогих ресурсов; мониторить память и предотвращать утечки.

### Testing Strategy — стратегия тестирования

ASCII-пирамида тестов: **E2E** (мало) наверху → **Integration** (некоторое количество) → **Unit** (много) в основании. Что тестировать: Unit — бизнес-логика, утилиты, чистые функции, алгоритмы; Integration — взаимодействие компонентов, потоки данных, внешние сервисы; E2E — критические пользовательские сценарии.

### Anti-Patterns to Avoid — анти-паттерны

- ❌ **God Object** — один класс, который знает/делает слишком много.
- ❌ **Spaghetti Code** — запутанный неструктурированный код с неясным потоком.
- ❌ **Magic Numbers** — хардкодные значения без объяснения: плохо `if user.age > 18`, хорошо `MINIMUM_AGE = 18; if user.age > MINIMUM_AGE`.
- ❌ **Circular Dependencies** — модуль A зависит от B, B зависит от A.
- ❌ **Premature Optimization** — оптимизация до выявления реальных узких мест.

### Architecture Review Checklist — чек-лист ревью архитектуры

- **Structure**: чёткое разделение concerns; консистентная структура папок; логичные границы модулей.
- **Dependencies**: нет циклических зависимостей; используется DI; абстракции вместо конкретики.
- **Scalability**: компоненты/сервисы stateless где возможно; доступ к данным оптимизирован (индексы, кэш); эффективное использование ресурсов; система выдержит рост нагрузки.
- **Maintainability**: код самодокументируемый; консистентные имена; легко добавлять фичи.
- **Testability**: бизнес-логика изолирована; зависимости можно замокать; покрытие тестами адекватное.

### When to Refactor Architecture — 5 признаков необходимости архитектурных изменений

1. Добавлять фичи становится всё труднее.
2. Изменения в одной области ломают несвязанные области.
3. Тесты сложно писать или они хрупкие.
4. Дублирование кода повсюду.
5. Проблемы производительности при масштабировании.
