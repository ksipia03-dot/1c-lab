# Скилл `code-quality-standards` — стандарты качества кода

## Назначение и тип

Скилл определяет **стандарты качества кода, лучшие практики и паттерны рефакторинга**: принципы читаемости (Readability, DRY, KISS, YAGNI), каталог запахов кода с приёмами исправления, лучшие практики (обработка ошибок, null-safety, иммутабельность, чистые функции), чек-листы рефакторинга и ревью, метрики сложности и каталог паттернов рефакторинга.

**Тип: гайдлайн** (справочник). Не содержит сценария исполнения — это свод правил, который **читают агенты перед работой**, чтобы писать, ревьюить и рефакторить код по единым стандартам. Финальная пометка оригинала: стандарты должны применяться консистентно по всей кодовой базе; агенты обязаны ссылаться на этот скилл при написании, ревью и рефакторинге кода.

## Подробный пересказ содержимого

### Code Quality Principles → 1. Readability (читаемость)

Девиз: «Код читают в 10 раз чаще, чем пишут. Оптимизируй под чтение».

- **Clear Naming** — пример: ✅ `calculateMonthlyPayment(principal, rate, months)` — самодокументируемо; ❌ `calc(p, r, m)` — непонятно.
- **Small Functions** — максимум 20–30 строк на функцию; один уровень абстракции на функцию; функция делает одну вещь хорошо. Пример: ✅ `validateEmail` + `validatePassword` (каждая в 1 строку) и композиция `validateUser = validateEmail AND validatePassword`; ❌ `validateUser` на 50+ строк валидационной логики.

### 2. DRY (Don't Repeat Yourself)

Пример: ❌ `getActiveUsers` и `getActivePosts` дублируют условие `status == 'active' AND deletedAt == null`; ✅ общее условие вынесено в `isActive(item)`, обе функции используют `filter(..., isActive)`.

### 3. KISS (Keep It Simple, Stupid)

Предпочитать простые решения: ✅ `isEven(n) → n % 2 == 0`; ❌ оверинжиниринг `isEven(n) → (n & 1 == 0) ? true : false`.

### 4. YAGNI (You Aren't Gonna Need It)

Не добавлять функциональность, пока она не нужна: ❌ класс `User` с полями `phone` («а вдруг?»), `fax` («на всякий случай»), `twitter` («почему бы и нет»); ✅ только то, что нужно сейчас: `name`, `email`.

### Code Smells & Refactoring — 7 запахов кода с приёмами исправления

| # | Запах | Признак | Как рефакторить |
|---|-------|---------|-----------------|
| 1 | **Long Method** | Функция > 30 строк | Извлечь меньшие функции |
| 2 | **Large Class** | Класс со слишком многими обязанностями | Разбить на меньшие классы (SRP) |
| 3 | **Long Parameter List** | Функция с 4+ параметрами | Объект-параметр или builder: ❌ `createUser(name, email, age, address, phone)` → ✅ `createUser(params: CreateUserParams)` |
| 4 | **Duplicated Code** | Один и тот же код в нескольких местах | Извлечь в общую функцию/класс |
| 5 | **Primitive Obsession** | Примитивы вместо маленьких объектов | Создать value objects: ❌ `sendEmail(email: String)` без валидации → ✅ класс `Email`, который валидирует строку в конструкторе (кидает `Error('Invalid email')`) и гарантирует валидность везде |
| 6 | **Feature Envy** | Метод использует данные чужого класса больше своего | Перенести метод в тот класс |
| 7 | **Dead Code** | Неиспользуемые функции, переменные, импорты | Удалить |

### Best Practices — 4 лучшие практики

1. **Error Handling** — специфичные типы ошибок: ✅ класс `ValidationError extends Error` с `this.name = 'ValidationError'`, и catch разделяет `ValidationError` от остальных; ❌ общий `catch error: log('Error:', error)` — всё в одну кучу.
2. **Null Safety** — явная обработка null: ✅ `getUser(id): User or null` + проверка `if user is not null` перед использованием; ❌ `getUser(id): User` с потенциальным null внутри — `print(user.name)` может упасть.
3. **Immutability** — ✅ `updatedUser = copyWithChanges(user, { name: 'New Name' })` (новый объект); ❌ `user.name = 'New Name'` (мутация существующего).
4. **Pure Functions** — ✅ `add(a, b) → a + b`; ❌ функция с побочным эффектом, которая накапливает внешний `total` (изменяет внешнее состояние).

### Refactoring Checklist — чек-лист рефакторинга

- **До**: тесты на месте (чтобы проверить, что поведение не изменилось); запах идентифицирован; техника рефакторинга выбрана.
- **Во время**: маленькие инкрементальные изменения; запускать тесты после каждого изменения; коммитить после каждого успешного рефакторинга.
- **После**: все тесты по-прежнему проходят; код стал читаемее; сложность снижена; новых багов не внесено.

### Complexity Metrics — цикломатическая сложность

| Значение | Оценка |
|----------|--------|
| **1–5** | Простой код, низкий риск |
| **6–10** | Умеренная сложность |
| **11–20** | Высокая сложность, стоит рефакторить |
| **21+** | Очень высокий риск, рефакторить обязательно |

Пример высокой сложности: `processOrder(order)` с тройной вложенностью if (`status == 'pending'` → `total > 1000` → `customer.vip` …) и веткой `else if status == 'shipped'` — вместо этого лучше полиморфизм или паттерн Strategy.

### Code Review Checklist — чек-лист ревью (4 категории)

- **Readability**: ясные имена переменных/функций; функции маленькие и сфокусированные; комментарии объясняют «почему», а не «что»; консистентное форматирование.
- **Maintainability**: нет дублирования; Single Responsibility; низкая связанность, высокое сцепление; легко расширять.
- **Correctness**: обработаны граничные случаи; обработка ошибок реализована; валидация ввода присутствует; тесты покрывают основные сценарии.
- **Performance**: нет очевидных узких мест; используются эффективные алгоритмы; запросы к БД оптимизированы; нет лишней работы.

### Common Refactoring Patterns — 5 паттернов рефакторинга

1. **Extract Method** — разбить длинный метод на меньшие.
2. **Rename Variable/Method** — использовать описательные имена.
3. **Replace Magic Number with Constant** — было `if (age > 18)`, стало `LEGAL_AGE = 18; if (age > LEGAL_AGE)`.
4. **Introduce Parameter Object** — заменить длинные списки параметров объектами.
5. **Replace Conditional with Polymorphism** — заменить if/switch иерархией классов.
